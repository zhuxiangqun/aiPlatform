# aiPlat / Pi / 本体 / FDE / 诊断平台：评审与首个纵向切片执行计划

> 目的：首阶段摘要。**完整落地方案（执行真源）**见 [landing-plan](./ai-platform-five-products-landing-plan.md)；冲突以落地方案为准。  
> 与[目标架构与 ADR 母稿](./ai-platform-five-products-target-architecture.md)配套。本文件不要求大规模搬目录，也不授权拆成五个服务。  
> **批准只覆盖盘点、契约最小版和切片准备；不批准全面重构、目录搬迁或五服务拆分。**

## 1. 执行摘要

本轮只做四件事：

1. 以源码和可重复行为证据盘点现状，识别真实产品边界、依赖和数据 owner。
2. 定义最小跨产品契约与兼容矩阵，尤其是控制面失联、身份和版本语义。
3. 选一条真实客户场景，完成最小端到端交付切片：

   ```text
   FDE 建场景 → aiPlat 发布 Agent Bundle → Pi 部署运行
   → 诊断关联证据（Pi + aiPlat）→ FDE 验收
   （本体查询非必经；场景需要时只读评估）
   ```

4. 根据切片暴露的问题决定下一步模块化、产品化和部署拆分，不预设全面改造。

### 本轮不做

- 五产品目录整体搬迁或拆成五个仓库/微服务。
- 一次性建立完整诊断/自动修复平台。
- 将 FDE 扩展成通用项目管理系统。
- 将本体、诊断数据库全部迁出 Core。
- 将当前 Pi Thin 能力宣传为已完成 Enterprise Runtime。
- 未有客户和运维证据时拆分控制面、身份或连接器平台。

## 2. 治理和责任

启动前需指定以下角色。一个人可以兼任多个角色，但不可无人负责：

| 角色 | 责任 |
|---|---|
| 架构决策 owner | 维护产品边界、依赖方向和 ADR；裁决冲突 |
| 业务场景 owner | 提供真实场景、客户价值、验收人和业务失败成本 |
| 五产品 owner | 分别确认 aiPlat、Pi、本体、FDE、诊断范围和支持责任 |
| 安全/身份 reviewer | 审核身份透传、策略、密钥和副作用授权 |
| 测试/验收 owner | 建立可重复环境、运行验收并保存证据 |
| 运维 owner | 定义部署、升级、告警、备份恢复和故障处理 |

产品定义、数据 owner、契约规范和兼容矩阵的**单一事实源**是[目标架构与 ADR 母稿](./ai-platform-five-products-target-architecture.md)。本执行计划只记录本轮范围、决策、验收与责任；如摘要与母稿冲突，以评审后更新的母稿为准。

### 2.1 暂停条件

遇到以下任一情况，应暂停扩大范围，先重新评审边界或场景：

- 找不到真实 caller 或真实用户场景，只能用静态文档推断。
- 同一数据对象出现多个权威 owner，且短期无法裁决。
- 身份、租户或执行授权无法在目标服务端验证。
- Pi Runtime 无法在目标环境按支持方式安装、升级或观测。
- 本体查询没有来源/版本信息，诊断无法判断数据时效。
- 诊断只能给出无法重现或无法追溯的“健康分/结论”。
- 纵向切片需要先大规模搬目录、改数据库或全面重写接口。

## 3. 阶段 0：源码现状盘点

### 3.1 目标

确认“现在实际运行什么、谁调用谁、谁拥有数据”，不把架构文档、能力清单或代码目录当作实现证据。

### 3.2 两档盘点范围

**Gate 1 前必做：仅盘纵向切片路径。** 定位切片将经过的产品入口、实际 caller、数据 owner、身份流、副作用点、版本信息和运行证据。切片外模块不作为启动前置条件。

**Gate 2 前按需后置：切片外盘点。** 仅当切片暴露重复 owner、共享数据库、外部平台接入或独立部署需求时扩大调查。全仓目录考古、全面代码依赖图和所有能力条目的证据升级不属于 WP0。

WP0 有 **2 周时间盒**。到期必须提交“切片路径事实清单”，边按 **As-Is / Known Gap / Blocker** 登记（详见落地方案 §3.6）；切片外后置。**Blocker**（安全/权威/授权未知或不可控、无负责人）挡在 Gate 1 外；**Known Gap**（有拟建设计与负责人）可随 Gate 1 带入 WP3–WP4。**不要求** Gate 1 前已有端到端 E3。

### 3.3 盘点维度（限定到切片）

若切片路径不经过某产品，该产品对应盘点维度标注“切片未使用”并跳过，不阻塞 Gate 1；仅在切片需要该产品的接口、数据或权限时补盘。

- aiPlat：身份、资产管理、Agent 发布、执行和审计入口。
- Pi：`packages/aiplat-pi-runtime/` 的入口、扩展、导出包、配置、测试和关闭实验。
- 本体：Ontology 模型、数据映射、查询、图谱、治理和存储 owner。
- FDE：项目/场景/需求/实施/验收实际对象和 API。
- 诊断：监控、评估、测试、报告实际代码与数据模型，区分各层诊断 API 和管理端页面。
- 横向：数据库直连、内部 import、身份透传、事件、缓存、错误降级和重复实现。

### 3.4 证据分类

每项能力标一个证据等级：

| 等级 | 证据 | 可支持的结论 |
|---|---|---|
| E0 | 文档/声明/能力清单 | 仅说明设计或声明存在 |
| E1 | 源码入口和静态路径 | 代码存在、可识别依赖关系 |
| E2 | 单元测试/离线 smoke | 指定局部逻辑通过，不证明真实集成 |
| E3 | 多服务集成测试 | 指定服务组合和环境下接线有效；纵向切片路径关键能力的最低证据级别 |
| E4 | 干净部署/真实模型或真实平台验收 | 指定版本和环境下端到端行为成立；对外承诺能力的最低证据级别 |
| E5 | 生产运营数据 | 运行可靠性和实际使用表现 |

不能把低等级证据表述为高等级结论。

### 3.5 阶段产物

1. 产品能力和入口清单（含 owner、代码路径、caller、证据级别）。
2. 真实依赖图：代码 import、HTTP/RPC、数据库、事件和缓存边。
3. 数据 owner 表：实体、主存储、写入方、读取方、备份/删除责任。
4. 身份与副作用流图：谁签发身份、谁授权、谁执行写操作。
5. 关闭/归档实验清单，特别是 Pi 厂内编码执行路径。
6. 已知差距清单，按安全、正确性、产品边界、可运维性分级。

### 3.6 通过标准

- 纵向切片涉及的每条调用边有可定位代码入口和实际 caller。
- 每类切片数据有唯一 owner，缓存和派生数据单独标出。
- 能区分 Pi Thin 已实现内容与 Enterprise Runtime 的缺口。
- 诊断当前已有能力与目标 MVP 的差异清楚。
- 所有“已接线/已可用”声明都标有对应证据等级。
- 纵向路径关键能力至少 E3；对外产品承诺至少 E4。未达标时降级表述或标记待验证。

## 4. 阶段 1：契约与兼容矩阵

### 4.1 原则

先定义最少的跨产品契约，不先创建完整公共平台或新服务。契约要求可版本化、可测试、可向后兼容，并允许不同实现接入。

### 4.2 必需契约

| 契约 | 最小内容 | 验收问题 |
|---|---|---|
| Agent Bundle | 资产 ID、来源版本、manifest schema、权限声明、Runtime 范围、签名/完整性、回滚信息 | Pi 能否拒绝不兼容或损坏的包？ |
| Runtime API | 注册、心跳、部署状态、健康、配置版本、事件上报、命令身份、离线语义 | 控制面断开时 Pi 的状态与副作用是否明确？ |
| Semantic API | Ontology/Mapping 版本、查询、权限、来源、新鲜度、错误 | 消费者能否判断结果来自哪个模型/数据版本？ |
| Evidence/Diagnosis | 事件 schema、source、版本、run/trace 关联、证据引用、报告版本 | 报告是否可追溯、复现并处理过期数据？ |
| Delivery API | 项目/场景 ID、交付状态、版本引用、任务和验收证据 | FDE 是否可编排而无需共享对方数据库？ |
| Identity/Policy | Tenant/Actor、service identity、scopes、audience、request ID、授权失败 | 最终授权是否在目标服务执行？ |

### 4.3 最小版本兼容矩阵

阶段 1 必须填充实际版本和 owner，不能只保留模板：

| 对象 | 生产者 | 消费者 | 兼容策略 | owner |
|---|---|---|---|---|
| Agent Bundle schema | aiPlat 工厂 | Pi Runtime | 支持范围声明；不兼容时安装前拒绝 | 待指定 |
| Runtime API | Pi / 控制面 | aiPlat 或外部控制面 | 向后兼容窗口、废弃通知、重试/幂等 | 待指定 |
| Ontology model/query schema | 本体平台 | aiPlat/Pi/FDE/诊断 | 版本不可变，迁移需报告和回滚点 | 待指定 |
| Evidence/Event schema | 各产品 | 诊断 | schema 版本、未知字段处理、回放 | 待指定 |
| Delivery schema | FDE | 各产品 adapter | 状态转换幂等、外部数据用稳定引用 | 待指定 |
| Identity/Policy schema | aiPlat 或外部 IAM | 所有服务 | audience/scope/tenant 校验、密钥撤销 | 待指定 |

### 4.4 控制面不可用行为

阶段 1 逐产品决策，不允许使用含糊的“尽量继续”：

| 产品/操作 | 建议默认行为 | 必须评审的例外 |
|---|---|---|
| Pi 读取已签名、本地仍有效的 Agent bundle | 可继续有限运行，记录离线状态 | 策略过期后的最长宽限期 |
| Pi 发起高风险工具副作用 | fail-closed | 明确的本地授权与审计机制 |
| 本体只读查询 | 可返回带版本的新鲜缓存或明确 unavailable | 数据敏感级别及缓存期限 |
| FDE 读取已有项目 | 可展示最后同步状态并标 stale | 离线编辑冲突策略 |
| 诊断接入中断 | 记录未送达并标记证据缺口 | 本地缓冲期限/数据删除 |

## 5. 阶段 2：最小纵向切片

### 5.1 目标

用一条有限、可回滚 Agent 或 Runtime 版本、可验收的业务路径验证五产品边界，而不是先搭五套产品目录或服务。优先使用真实客户路径；内部场景 fallback 见 5.2。

### 5.2 场景选择条件与 fallback

选一个同时满足以下条件的场景：

- 有明确业务用户和验收人。
- 有可重复输入、预期结果和失败条件。
- 若场景依赖语义数据，则使用一个明确的本体模型或语义查询；否则本体步骤标「切片未使用」。
- Agent 工作范围和可执行工具有限。
- 可在隔离环境部署 Pi Runtime。
- 能产生可关联的运行证据，且不要求先重构大部分系统。

优先选真实客户场景。若暂无可用客户场景，允许用**内部可复现等价场景**启动，但必须有明确业务 owner、输入/预期结果、验收标准和失败成本定义，并标注“非客户验收”。内部场景只能验证技术闭环，不能证明客户价值；Gate 2 扩大产品化前，必须由至少一个真实客户场景替换或背书。

不选跨多个业务域、必须接生产敏感数据或依赖大范围未完成能力的场景作为第一条路径。

### 5.3 流程与责任

| 步骤 | 责任产品 | 输入 | 输出/证据 |
|---|---|---|---|
| 场景建档、需求和验收定义 | FDE | 客户问题、使用者、成功/失败标准 | Scenario、Requirement、Acceptance Criteria |
| 语义/数据准备评估（可选） | 本体 | 目标业务问题、数据源 | Ontology/Mapping 版本、查询计划、质量与来源报告；路径不依赖则可跳过 |
| Agent 资产构建和发布 | aiPlat | 场景需求、模型/工具权限 | 版本化 Agent Bundle、权限声明、发布审计 |
| 目标环境部署与执行 | Pi | Bundle、Runtime 配置、凭据/策略 | Runtime 版本、执行 run/trace、结果和执行事件 |
| 运行证据接入和诊断报告 | 诊断 | 首切片只接 **Pi + aiPlat** 的事件、run/trace 与 Agent/bundle 版本 | 可追溯报告、缺失/过期证据状态 |
| 客户验收与交接 | FDE | 运行结果、诊断证据、验收标准 | 验收结论、例外项、交接记录 |

### 5.4 最小功能范围

- 一个客户/项目/场景。
- 一个 Agent Bundle 和一个 Pi Runtime 环境。
- 一个低风险工具或只读操作；高风险副作用不纳入首切片。
- 一个可关联的诊断报告，至少关联 Runtime、Agent/bundle 版本和 run/trace ID（证据源：Pi + aiPlat）。
- 本体域/受控查询：仅当场景需要；非 Gate 1 阻塞项。
- 本体和 FDE 诊断 adapter 不属于首切片阻塞项，可在切片验证后独立排期。
- 一个 FDE 验收记录。
- 一个服务失联/权限拒绝/过期语义测试。

### 5.5 验收标准

**端到端正确性**

- 可从 FDE 记录的需求定位到 Agent、Bundle、Pi 实例及诊断报告；若本切片执行了本体步骤，则须含 Ontology 版本。
- Pi 在目标环境运行指定 Agent，输出符合预先定义的结果契约。
- 若启用本体：结果带来源及版本；诊断首切片不强制自动接入本体事件。
- FDE 可按验收标准接受或拒绝交付，结果有证据。

**安全与失败模式**

- 服务端验证 tenant、actor、scope 和目标资源权限。
- 无授权工具调用被拒绝；客户端开关不能绕过服务端授权。
- 控制面失联时高风险副作用按决策 fail-closed。
- 无法获取本体/遥测时标明 unavailable/stale，不生成伪健康结论。
- 日志和诊断证据脱敏，不泄露 token 或敏感内容。

**可重复性与运维**

- 在干净环境从 bundle 安装到验收可按文档重跑。
- 保存代码版本、配置版本、bundle、Runtime、Ontology 和诊断规则版本。
- 失败可定位到具体产品边界，能回滚 Agent 或 Runtime 版本。
- 记录执行时长、部署成功率、错误类型、人工介入点和资源成本。

### 5.6 退出/暂停条件

- 若切片要靠跨域数据库直写才能跑通：暂停，先补公开接口。
- 若权限只能由 Pi 客户端判断：暂停，不上线副作用操作。
- 若本体结果没有来源/版本：先补数据契约，不进入验收阶段。
- 若诊断无法关联源证据：缩小报告结论，不以总分代替证据。
- 若 FDE 只记录项目状态却无法产生验收证据：重新定义交付闭环。
- 若所有失败都要求同步改五个产品：检查契约是否过度耦合。

## 6. 阶段 3：仅对切片暴露的问题模块化

切片通过后再安排模块化，不预先全仓搬迁：

1. 对真实跨产品调用边添加 facade 或 adapter。
2. 对跨域数据库访问逐条替换，保留兼容读路径和回滚窗口。
3. 增加依赖守卫：产品间只能依赖契约包/公开 API。
4. 将不稳定实验和已关闭路径移出产品主入口及正常发布清单。
5. 对稳定 API 增加契约测试和版本兼容测试。
6. 目录移动每次限制在一个产品子域，并由行为回归保护。

目录重排不是阶段目标。目标结构只在模块和 owner 稳定后逐步采用。

## 7. 诊断 MVP 范围控制

首切片只交付：

1. Pi 与 aiPlat 两条证据流的最小接入；本体和 FDE adapter 后置，不能阻塞切片。
2. 按 tenant、product、environment、asset version、run/trace 关联。
3. 输出可回溯报告，记录证据来源及规则/评测版本。
4. 明确区分 healthy、degraded、failed、unknown、stale；缺证据不得默认 healthy。
5. 生成修复建议或 FDE 任务，不直接执行跨平台修改。

暂缓：通用告警中心、全功能测试编排器、自动根因修复、跨平台自动发布、独立工单系统。后续按用户需求和 MVP 使用数据排优先级。

## 8. FDE MVP 范围控制

首切片围绕“场景到验收证据链”，只强制使用 **Engagement、Scenario、Requirement、DeliveryPlan、Evidence、Acceptance** 六类对象。Decision、Assessment、Task、Handover 在实际流程需要时再引入。

暂缓：通用甘特图、资源财务、人力排期、全能 CRM、通用工单系统。必要项目管理功能通过现有系统 adapter 接入。

## 9. 产品 owner、指标与运营决策

切片开始前指定五个产品 owner。建议每个产品只选 2–4 个能推动决策的首要指标：

| 产品 | 首轮指标 |
|---|---|
| aiPlat | Agent 发布成功率、策略执行正确率、审计证据完整率 |
| Pi | 安装/升级成功率、任务成功率、断连降级正确率 |
| 本体 | 查询可追溯率、映射关键字段覆盖率、数据新鲜度 |
| FDE | 场景到验收周期、验收证据完整率、返工率 |
| 诊断 | 证据关联成功率、报告可复现率、unknown/stale 正确识别率 |

指标需写定义、分母、采集源、目标值和 owner。首切片先建基线，不应在无历史数据时虚构成熟度目标。

## 10. 工作分解与交付物

| 工作包 | 主要产物 | 前置条件 | 完成判据 |
|---|---|---|---|
| WP0 现状盘点 | 代码/调用/数据/身份/证据图、差距清单 | 架构+业务 owner；场景与验收人（五产品 owner 可周内补齐） | 纵向路径涉及的事实可追溯 |
| WP1 产品决策 | 产品边界、非目标、owner、指标 | WP0 初步完成 | 五产品间无悬空职责和双重 owner |
| WP2 契约 | 六类契约、兼容矩阵、失联语义 | WP1 评审通过 | 生产者/消费者/版本/降级均有 owner |
| WP3 切片设计 | 场景、流程、数据、权限、测试计划 | WP2 最小版本可用 | 可在隔离环境重复执行 |
| WP4 切片执行 | 可运行链路、证据、运维手册 | WP3 安全评审通过 | 验收表全部通过或问题明确归因 |
| WP5 架构回顾 | ADR 更新、迁移/backlog、拆分建议 | WP4 结束 | 每项后续改造有证据和收益理由 |

具体负责人、工期和容量应在 WP0 后估算，不在缺少现状数据时预设日期。

## 11. 决策门与拆分判断

### Gate 1：是否进入纵向切片（≠ L1；单独批准）

须同时满足 Decision Brief 5 项、目标环境、数据 owner、授权路径、启用集契约最小版；**无未关闭 Blocker**；Known Gap 含拟建面/负责人/测试/回滚。未使用产品标「切片未使用」。**不要求**路径已具备端到端 E3（由 WP4 交付，完成标准不降）。权威细则：落地方案 §3.6 / Gate 1 检查单。

### Gate 2：是否扩大产品化

须满足：WP4 端到端行为通过；失败可观察；边界成立；产品 owner 到位；**D13 书面客户背书**（或真实客户场景）。仅「非客户验收」不可过 Gate 2。

### Gate 3：是否独立部署某产品

需有以下证据之一，并完成成本比较：

- 客户隔离/数据驻留/合规强制要求。
- 实际负载要求独立扩缩容。
- 独立 SLA 和发布节奏已有责任团队承接。
- 多平台复用已通过至少两个真实消费者证明。
- 共享部署已造成可量化的故障或升级冲突。

若没有独立 owner、on-call、备份恢复和升级能力，即使技术上可拆也不应拆。

## 12. 风险登记表

| 风险 | 早期信号 | 控制措施 |
|---|---|---|
| 改造范围膨胀 | 同时新建五套 API/服务/目录 | 限定首切片和 MVP；范围变化须决策记录 |
| aiPlat 隐性单体 | 外部产品 import 私有模块 | 契约测试、依赖守卫、外部 adapter |
| Pi 过度承诺 | 将 Thin 包等同 Enterprise Runtime | 产品形态矩阵、证据等级、安装验收 |
| 本体和 RAG 混淆 | 多份数据互相声称权威 | owner、版本和派生缓存标记 |
| FDE 膨胀成项目管理系统 | 需求集中于甘特/工单而无交付证据链 | MVP 对象和非目标锁定 |
| 诊断膨胀 | 同期做全监控、全测试和自动修复 | MVP 限定证据接入、关联和报告 |
| 权限旁路 | 只依赖 Pi UI/客户端 gate | 目标服务端授权；负向测试 |
| 无证据的“成功” | 缺数据仍显示健康/通过 | unknown/stale 状态作为硬验收 |
| 兼容性破坏 | Runtime、bundle、Ontology、event 同步升级 | 版本矩阵、兼容测试、双版本窗口 |
| 产品 owner 缺席/频繁更换 | 决策无人签署、责任边界反复变化 | 由架构决策 owner 与业务场景 owner 联合冻结切片启动；先补单一 owner 和替补人 |
| 评审决策长期悬空 | 关键权限/数据决策超过约定期限 | 升级给架构决策 owner 裁决并留记录 |
| 切片被业务优先级挤占 | 人员不可用、验收反复延期 | 正式暂停并保留 WP0/WP1 产物；重启重过 Gate 1 |

## 13. 评审会议决策清单

评审会当场必须决定的五项见 [Decision Brief](./ai-platform-five-products-decision-brief.md)：场景、业务验收人、Pi 形态、控制面/IAM、Gate 1 与暂停签署角色。以下其余事项指定 owner、截止日期和所需证据，不要求一次会议全部裁决：

1. 本体数据源、模型版本和查询 owner 是谁？
2. 诊断首切片接入哪些 Pi/aiPlat 事件，明确排除哪些？
3. 客户数据、日志、Prompt 和模型输出的保留/脱敏/删除规则是什么？
4. 五产品 owner、on-call 和核心指标负责人是谁？
5. 哪些现有代码路径必须复用，哪些属于关闭/归档实验？
6. Gate 2/3 的通过与暂停决策由谁签署？

暂停由架构决策 owner 与业务场景 owner 联合判定；理由、证据、影响和恢复条件写入对应 ADR/评审记录。恢复需同一组角色签署，不得由单一产品 owner 单方面推翻。

## 14. 计划结论

此执行计划不要求“五产品全面开工”。先做源码现状盘点和最小契约，再跑通一条有客户价值、可隔离、可重复、可验收的纵向路径。切片通过后，仅模块化真实暴露出的边界；独立部署由客户、SLA、负载、团队和成本证据决定。

**批准本计划，意味着批准进入盘点与切片准备；不意味着批准五产品全面重构、目录搬迁或微服务拆分。**
