## 第一部分：问题与方向（5 分钟 · 对应 PPT 2–4）

### 我们要解决什么

仓库里已经同时长出了控制面、Runtime、本体/知识、FDE、诊断相关能力，但对外叙事容易混：

- **Pi** 被当成「缩小版 aiPlat」，承诺了集中治理它并不具备；  
- **本体与 RAG/Knowledge** 谁是权威事实说不清；  
- **FDE** 容易变成若干页面 + 直调 Core 内部，而不是有自己数据与验收对象的交付产品；  
- **诊断** 容易等于 Management 仪表盘，缺跨产品证据链；  
- **静态门禁 / 能力清单变绿** 被误当成生产就绪。

### 我们主张的方向（四句话）

1. 定义五个**产品域**：aiPlat、Pi、本体、FDE、诊断。  
2. **产品独立 ≠ 立刻微服务**；先产品 / 接口 / 代码边界，部署按需再拆。  
3. **aiPlat 提供默认控制面**（身份、策略、审批、审计），契约可换外部 IAM；各产品本地仍要鉴权。  
4. **一条真实纵向切片**验证协作；切片暴露的问题才进入模块化——禁止五线齐开。

（投第 3 页五产品表，口头各一句即可，勿逐格念。）

## 第二部分：本次批准范围（4 分钟 · 对应 PPT 5）

### 请批准（L1 · 有条件）

1. **WP0**：只盘**纵向切片路径**上的 caller、数据 owner、身份与副作用，时间盒 **≤2 周**；边登记为 **As-Is / Known Gap / Blocker**（§3.6）。  
2. **WP1–WP2**：冻结该路径**启用集**最小契约、兼容矩阵、失联语义（未启用类不阻塞）。  
3. **准备**目标路径：`FDE → aiPlat Bundle → Pi → 诊断（Pi+aiPlat）→ FDE 验收`；**开跑须另批 Gate 1**，本次**不批准 WP3–WP4**。

### 请明确不批准

- WP3–WP4 / 宣称「切片已开跑」；  
- 五个仓库 / 五个数据库 / 五个微服务；  
- 全仓目录搬迁；诊断全套 + 自动跨平台修复；  
- FDE 做成通用项目管理；宣传 Pi Thin = Enterprise Runtime；  
- 无客户背书时过 Gate 2；无证据时拆共享控制面。

**一句话收束**：批准的是「查清事实并形成可测契约」，不是「开始建切片或大搬家」。

## 第三部分：会上必须拍板的五项（8 分钟 · 对应 PPT 6）

请主席按表逐项确认，建议默认如下；有异议当场改，不留「会后再说」的身份/安全项。

### 决策 1 — 首切片场景

- **问业务**：会前提名的场景是哪一个？验收标准能否一句话说清？  
- **建议**：优先真实客户；否则内部可复现场景，必须标「非客户验收」，Gate 2 扩大前要客户场景替换或背书。  
- **记录**：场景名、输入、成功/失败标准。

### 决策 2 — 业务验收人

- **问**：谁签字认「业务结果成立 / 不成立」？不能是纯开发自测。  
- **记录**：姓名 + 角色；无验收人 → **不开 Gate 1**。

### 决策 3 — Pi 首切片形态

- **建议默认**：Pi **Thin**（**已签名 Bundle 落盘后**，执行阶段可按离线策略在 aiPlat 断连下继续；**不是**整条发布+诊断都不依赖 aiPlat）。  
- 若选 Enterprise：必须列出**本次实际验证的子集**，禁止口头「Enterprise 全做」。  
- **记录**：Thin / Enterprise子集清单。

### 决策 4 — 控制面 / IAM

- **建议默认**：aiPlat 默认控制面。  
- 若客户外部 IAM：指定 adapter 责任人；**禁止** aiPlat 与外部双重授权并行且责任不清。  
- **记录**：aiPlat 默认 / 外部 IAM 名称；安全 reviewer 是否同意。

### 决策 5 — Gate 1 与暂停签署

- **建议**：架构决策 owner × 业务场景 owner **联合**签 Gate 1；暂停与恢复同一组人。  
- **强调**：单一产品 owner 不得单方面恢复已暂停范围。  
- **记录**：两人姓名 + 替补人。

（五项记入决议页；未决的非阻塞项另表，带 owner 与截止日期。）

## 第四部分：Gate、时间盒与成功标准（4 分钟 · 对应 PPT 7–8）

### 节奏

```text
[L1] WP0–WP2 → [另批] Gate1 → WP3–WP4 → [另批] Gate2 → [另批] Gate3
```

- **Gate 1**：无 Blocker；场景/验收人/环境/数据 owner/授权/启用集契约齐；Known Gap 可带设计进 WP3–WP4。**不要求**开工前已有端到端 E3。  
- **Gate 2**：WP4 通过 + **D13 客户背书原件**（§6.0.1 字段齐全，非仅「客户已同意」）→ 才扩大。  
- **Gate 3**：隔离/SLA 等证据 + 成本；架构×业务联签门禁（运维可为主 A 执行）。

### 成功标准

**L1 阶段**：事实可回溯；缺口分类正确；契约可测。  
**切片完成（Gate1 后）**：无未授权跨库直写；版本可关联；不伪报健康；路径 ≥ **E3**、对外 ≥ **E4**（不降标）。

## 第五部分：风险与暂停（2 分钟 · 对应 PPT 9）

只强调三条，避免吓退也避免轻视：

1. **范围膨胀** — 同时开五套 API/目录 → 打回，只保留切片。  
2. **权限旁路** — 只靠 Pi 客户端 gate → 安全否决，副作用不上线。  
3. **伪健康** — 缺证据仍绿 → 诊断结论作废，不得进验收「通过」。

暂停由架构 × 业务书面记录理由与恢复条件。

## 答疑备用（精简）

| 可能问题 | 建议答法 |
|----------|----------|
| 为什么不先拆微服务？ | 产品/接口/代码边界未证伪前，拆部署只会放大版本与故障成本；Gate3 有门槛。 |
| 和现有 CoreFacade / 分层是否冲突？ | 不冲突。控制面与公开契约强化 Facade；禁止的是跨产品私有 import 和共享库当契约。 |
| 诊断为什么首切片只接 Pi+aiPlat？ | 先打通证据链最小闭环；本体/FDE adapter 不阻塞首切片，Gate2 后按需加。 |
| 没有客户场景怎么办？ | 允许内部场景但标非客户验收；扩大产品化前必须客户背书。 |
| WP0 两周盘不完全仓？ | 本来就不盘全仓；只盘切片路径，其余标后置。 |
| 谁有权说「暂停」？ | 架构决策 owner 与业务场景 owner 联合；纪要留痕。 |
| 会不会影响当前 #379 类文档治理？ | 正交。五产品是架构域改造；文档治理继续按既有门禁，不混进本批准范围。 |
