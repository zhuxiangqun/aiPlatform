# aiPlat / Pi / 本体 / FDE / 诊断：Decision Brief

> 评审用途：请求批准有限的盘点、契约准备与一条纵向切片；不是全面重构授权。  
> **执行真源**：[落地方案](./ai-platform-five-products-landing-plan.md)。  
> 边界依据：[目标架构与 ADR 母稿](./ai-platform-five-products-target-architecture.md)。  
> **批准本 brief 不等于批准五服务拆分、全量目录搬迁或诊断平台全功能建设。**  
> 与落地方案冲突时以落地方案为准。

## 建议评审结论

**有条件批准 L1 执行基线**（[落地方案 v1.3](./ai-platform-five-products-landing-plan.md)）：书面获准见 [`reports/five-products/L1_AUTHORIZATION.md`](../../reports/five-products/L1_AUTHORIZATION.md)；§2.3 齐备后仅 **WP0–WP2**。**不批准** WP3–WP4，**不**解释为首切片已开跑或全面改造已获批。Gate 1 按 §3.6；Gate 2 须 D13 背书**原件**；Gate 3 不承诺日期。

## 本次批准

- 以源码、调用链和可重复行为证据为准盘点现状，不按文档声明直接认定实现状态。
- 仅盘点纵向切片涉及的调用边、数据 owner、身份流和副作用点；切片外全仓盘点后置。
- 定义切片必需的 Agent Bundle、Runtime、Semantic Query、Evidence/Diagnosis、Delivery、Identity/Policy 契约最小部分，并记录实际版本兼容关系。
- 准备一条范围受控、可回滚 Agent 或 Runtime 版本、可验收的纵向路径：

  ```text
  FDE 建场景 → aiPlat 发布 Agent Bundle → Pi 部署运行
  → 诊断关联证据出报告（Pi + aiPlat）→ FDE 验收
  ```

  本体查询**非必经**（场景需要时只读评估）；详见落地方案 §3。

- 诊断首切片只接 **Pi 与 aiPlat** 两条证据流，关联 run/trace 与 Agent/bundle 版本；本体和 FDE 诊断 adapter 可后续独立加入，不阻塞切片。
- 若没有真实客户场景，可用有业务 owner、验收标准和失败成本定义的内部可复现场景启动；须标注“非客户验收”，扩大产品化前必须由真实客户场景替换或背书。

## 本次不批准

- 五个产品拆成五个微服务、仓库、数据库或团队。
- 五产品代码目录整体搬迁或全面重写。
- 完整诊断套件、全平台自动根因修复或跨平台自动执行。
- 将 FDE 扩展成通用项目管理系统。
- 将当前 Pi Thin 包表述为完整 Enterprise Runtime。
- 缺少客户/运营证据时拆分共享控制面或新建第六个产品。

## 评审会必须拍板的 5 项

| # | 决策 | 建议结果 | 决策 owner |
|---|---|---|---|
| 1 | 首个纵向切片场景 | 业务侧会前提名客户场景；若暂无则提名内部可复现场景及业务 owner | 业务场景 owner |
| 2 | 业务验收负责人 | 业务侧会前提名能签署业务结果和失败标准的人 | 业务场景 owner |
| 3 | Pi 首切片形态 | Thin 或 Enterprise；若选 Enterprise，列明本次实际验证能力 | Pi 产品 owner |
| 4 | 控制面/IAM | aiPlat 默认控制面，或指定客户外部 IAM；禁止双重授权 | 架构与安全 owner |
| 5 | Gate 1 与暂停签署 | 指定架构决策 owner、业务 owner 和替补人 | 评审主席 |

第 1、2 项须由业务侧在会前 **3 个工作日**提交候选场景与验收人；评审会负责确认或裁决，不做现场海选。

## 其他决策

完整 ADR 清单见执行计划。评审纪要为未决事项指定**单一 owner、截止日期和所需证据**；未到期事项不阻塞切片，涉及身份、安全或数据权威的未决事项则阻塞相关功能启用。

## 时间盒与 Gate

- WP0 盘点最多 **2 周**。到期提交切片路径事实清单，边按 **As-Is / Known Gap / Blocker**（落地方案 §3.6）登记；切片外区域标为后置，不以“全仓未盘完”阻塞。
- **Gate 1（单独决策，≠ L1）**：无未关闭 Blocker；场景、验收人、目标环境、数据 owner、授权路径、启用集契约最小版明确；Known Gap 含拟建面/负责人/测试/回滚后可带入 WP3–WP4。**不要求**整条路径在开工前已有端到端 E3（E3 由 WP4 交付，完成标准不降）。
- Gate 2：WP4 行为与安全通过后，且满足 **D13 书面客户背书**（最低字段见落地方案 §6.0.1）或真实客户场景，才批准扩大产品化。
- Gate 3：独立部署须有客户隔离、SLA、扩缩容、合规或发布节奏证据 + 成本评估；**门禁**由架构 × 业务联签（工作包可由运维主 A 执行）。

暂停由架构决策 owner 与业务场景 owner 联合判定；理由和恢复条件写入 ADR/评审记录。恢复需同一组角色签署，不得由单一产品 owner 单方面推翻。

## 成功标准

### L1 / WP0–WP2（当前获准范围）

- 盘点结论可回溯到源码、测试，或标明的 **Known Gap / Blocker**（不得把缺口写成已接线）。
- WP0 时间盒内提交事实清单；切片外后置；主路径 **无未关闭 Blocker** 方可提交 Gate 1。
- 启用集契约可测；未启用类标「本切片未启用」。

### 切片完成时（仅 Gate 1 批准 WP3–WP4 之后）

- 纵向路径无未授权跨库直写；身份与副作用由目标服务端校验。
- 关键路径 ≥ **E3**；对外承诺 ≥ **E4**（标准不因「原先是 Known Gap」而降低）。
- Agent、Runtime、诊断证据版本可关联；若启用本体步骤则 Ontology 版本亦须可关联。
- 断连、无数据、过期不伪报成功/健康；切片可重复，FDE 有验收证据链。
