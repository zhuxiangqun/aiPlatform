# aiPlat / Pi / 本体 / FDE / 诊断平台：目标架构与 ADR 母稿

> 状态：目标架构提案，供评审与后续 ADR 拆分；不代表现有代码已达到该状态。  
> 原则：源码和可重复行为验收证明实现；本文件描述目标边界。  
> 本文不授权大规模目录搬迁、服务拆分或数据迁移。

## 1. 决策摘要

目标是形成五个产品域：

1. **aiPlat**：企业级 AI 控制与治理平台。
2. **Pi**：面向企业部署环境的 AI Runtime。
3. **本体平台**：企业语义数据资产与 AI 数据服务平台。
4. **FDE 平台**：面向 FDE 工程师的场景实施与交付平台。
5. **AI 诊断平台**：针对 AI 产品的评估、测试、监控与诊断平台。

五个产品在用户、价值、责任、路线图和数据 owner 上独立；通过公开、版本化的 API、SDK、事件契约组合。**产品独立不等于代码仓库、进程、数据库或团队必须立即独立。** 部署拆分由客户隔离、SLA、负载、合规、发布节奏及运维成本驱动。

当前推荐关系：aiPlat 提供默认企业控制面；Pi 承担部署侧运行；本体提供权威语义数据服务；FDE 编排客户交付；诊断消费各产品证据并形成可追溯分析。诊断不拥有被诊断系统的运行事实，也不默认执行跨平台修复。

## 2. 设计原则

### 2.1 产品边界与部署边界分离

- **产品边界**：用户、价值主张、责任范围、路线图和支持承诺。
- **接口边界**：公开 API、SDK、事件、兼容策略和错误语义。
- **代码边界**：模块 owner、允许依赖方向、可独立测试和替换。
- **部署边界**：进程、数据库、集群和发布单元，可按需求演进。

先建立前三种边界，再决定部署拆分。不得以目录很多或架构图好看作为拆服务理由。

### 2.2 权威事实由 owner 持有

每类数据只有一个权威 owner。其他产品可以保存带来源、版本和新鲜度标记的投影、缓存或索引，不得将其伪装成权威数据。

### 2.3 控制面默认可用、实现可以替换

aiPlat 提供身份、租户、策略、审批和平台审计的默认企业控制面实现。其他产品依赖稳定契约，不直接 import aiPlat 私有模块。外部 IAM 或客户控制面通过 adapter 接入；各服务仍需在本地执行授权和安全校验。

### 2.4 诊断使用证据，不取代事实或权限

诊断结论须引用数据源、版本、时间和规则/评测版本。无证据、来源不可读或数据过期时返回 unknown/stale。修复动作由目标产品的授权接口执行。

### 2.5 静态一致性不等于行为正确

文件存在、声明计数相符、符号登记、矩阵匹配或图谱节点存在只能证明相应静态关系。产品可用性、生产调用、权限正确性和端到端成功必须由行为验收证明。

## 5. 各产品目标边界

### 5.1 aiPlat：企业级 AI 控制与治理平台

**应负责**：企业 AI 资产目录与版本；Agent 生命周期；模型和工具治理；租户、身份与策略；运行编排；审批、配额、审计和平台运营；面向 Pi/本体/FDE/诊断的默认控制 API。

**应避免**：把所有业务流程放入 Core；通过私有 Python import 暴露控制面；直接拥有 FDE 项目、本体模型或诊断报告的权威数据。

### 5.2 Pi：企业部署 AI Runtime

目标形态：

| 形态 | 目标职责 | 依赖边界 |
|---|---|---|
| **Pi Thin** | 加载导出的 Agent/Skill/SOP，使用本地或远端模型，完成基本执行闭环 | 无需 aiPlat 服务即可完成声明的基础闭环；不宣称集中企业治理 |
| **Pi Enterprise Runtime** | Runtime 安装、注册、配置、升级、回滚、健康、资源约束、运行事件上报 | 可由 aiPlat 或外部控制面管理；本地执行规则有明确来源和离线语义 |
| **Pi + aiPlat** | Pi 执行、aiPlat 管理资产/身份/策略/审批/审计 | 服务端作最终授权；客户端 native tool gate 只作防旁路保护 |

当前 `packages/aiplat-pi-runtime/` 是薄 Runtime/工厂产物宿主的重要实现，不应单独代表完整 Enterprise Runtime 产品。厂内 Pi 编码执行实验保持关闭/归档状态，重新启用需独立 RFC、真实生产 caller 和行为验收。

### 5.3 本体平台：企业语义数据资产与服务

子域包括：

- **Model**：实体、关系、属性、约束、术语、模型版本。
- **Ingestion**：源连接、同步、权限与更新策略。
- **Mapping**：源字段到语义模型映射、覆盖率、质量问题。
- **Semantic Store**：图谱及派生视图，标明权威性。
- **Query/Reasoning**：查询、路径、规则、推理、指标和证据来源。
- **Governance**：变更评审、审批、发布、兼容和回滚。
- **API/SDK**：供 aiPlat、Pi、FDE 和第三方消费。

本体拥有领域模型与语义数据版本；aiPlat 拥有 Agent 执行时的检索/上下文编排。RAG、向量索引和缓存是派生视图，不自动成为本体事实源。

### 5.4 FDE：交付工程师工作平台

第一性对象是**客户场景到可验收交付证据链**，不是通用工单或项目管理系统。最小领域对象：Customer、Engagement、Scenario、Requirement、Decision、Assessment、DeliveryPlan、Task、Evidence、Acceptance、Handover。

流程：客户/场景建档 → 需求发现 → 价值与可行性评估 → 领域/数据评估 → 方案与计划 → 接入系统/数据/Agent/Runtime → 测试验收 → 交接和运营。

FDE 通过 adapter 编排 aiPlat、Pi、本体、诊断和客户既有平台；不直接读写这些产品的内部数据库。

### 5.5 诊断：跨平台 AI 质量与运行保障

**MVP 限定为**：证据接入、按 run/trace/version 关联、可追溯诊断报告、unknown/stale 处理。评估集和测试运行按第二阶段逐步产品化；自动修复后置。

长期子域可包括 Evaluation、Testing、Telemetry、Correlation、Diagnosis 和受控 Remediation。但修复由目标产品 API 执行并承担权限检查，诊断只提出建议或创建受控任务。

## 6. 共享能力及反单体约束

### 6.1 控制面

aiPlat 是默认控制面实现，但必须满足：

1. 对外提供版本化契约；跨产品禁止 import aiPlat 私有身份/策略实现。
2. 外部 IAM/控制面 adapter 从第一阶段定义，不等 Pi Enterprise 阶段再补。
3. 每个产品保留本地授权和审计责任。
4. 定义控制面不可用时的逐产品降级：只读、缓存策略、拒绝副作用或停止服务，不允许含糊的“尽量运行”。

### 6.2 共享基础设施与连接器

LLM Provider、数据库、向量、缓存、观测 SDK、MCP 和外部连接器作为共享组件/契约，不先创建第六个产品。凭证、权限、错误映射和版本兼容由统一 SDK/adapter 约定。

### 6.3 服务不可用语义

每个跨产品调用定义：超时、重试、幂等、错误类别、离线行为、缓存有效期、策略新鲜度、人工介入条件。安全相关副作用默认 fail-closed；只读能力可按明确策略使用带版本的新鲜缓存。

## 7. 数据所有权矩阵

| 数据对象 | 权威 owner | 其他产品允许持有 |
|---|---|---|
| Tenant/Actor/平台策略 | aiPlat 控制面（或配置的外部 IAM） | 有期限的授权上下文，不可自行扩权 |
| Agent/Skill/Workflow/Tool 资产版本 | aiPlat | Pi 部署快照、诊断引用、FDE 引用 |
| Runtime/Deployment/Instance 状态 | Pi | aiPlat 控制面投影、诊断遥测索引 |
| Ontology/Mapping/Semantic Dataset | 本体平台 | 消费者缓存，必须含版本和新鲜度 |
| 客户场景/交付/验收 | FDE | 其他产品的项目关联 ID |
| Eval/Test/Diagnostic Report | 诊断 | FDE/aiPlat 链接与摘要，不覆盖原始运行事实 |
| 源系统运行日志/业务事实 | 各源产品 | 诊断可保留受控遥测与证据引用 |

## 8. 五类核心契约

### 8.1 Agent Bundle Contract

包括 `bundle_id`、资产来源、Agent/Skill 清单、schema 版本、Runtime 兼容范围、权限声明、模型要求、构建来源、签名/完整性信息、升级和回滚元数据。Pi 不得仅凭 bundle 内的权限声明自我授权。

### 8.2 Runtime Control Contract

包括注册、心跳、部署、启动/停止、健康、配置版本、日志/事件上报、命令授权、离线期限和状态同步。命令具有 caller、tenant、scope、request ID、幂等键和审计关联。

### 8.3 Semantic Data Contract

包括 Ontology/Mapping 版本、查询 API、访问策略、数据来源、新鲜度、推理/查询证据、错误状态和兼容策略。结果需能说明“基于哪个语义模型与数据版本”。

### 8.4 Evidence / Diagnosis Contract

包括事件 schema 版本、source product/instance/environment、资产版本、时间、严重级别、request/run/trace 关联、脱敏证据引用、保留策略和诊断报告的评估/规则版本。

### 8.5 Delivery Contract

包括项目/场景 ID、需求和决策版本、交付任务状态、使用的 Agent/Runtime/Ontology 版本、验收标准、证据、人工批准和交接结果。FDE 不要求下游产品共享其数据库。

## 9. 版本兼容矩阵（阶段 1 的必交付物）

| 契约/资产 | 兼容对象 | 最低策略 |
|---|---|---|
| Agent Bundle schema | Pi Runtime | bundle 声明 schema 版本；Runtime 声明支持范围；不兼容时安装前拒绝 |
| Agent API / control API | Pi、FDE、诊断、本体 adapter | 向后兼容窗口、废弃通知、双版本期和升级顺序 |
| Ontology schema/model | aiPlat、Pi、FDE、诊断 | 模型版本不可变；迁移需兼容报告、审批和回滚点 |
| Evidence/Event schema | 全部生产者和诊断 | 消费者忽略未知可选字段；破坏性变化升主版本；保留重放能力 |
| Delivery API/schema | FDE adapter 与各产品 | 状态转换幂等；外部对象只存稳定引用，不复制权威数据 |
| Identity/Policy contract | 所有服务 | audience/scope/tenant 明确；服务端校验；密钥轮换与撤销语义 |

矩阵需填入实际版本、支持窗口和 owner 后才可作为生产兼容承诺。

## 11. 独立部署门槛

某产品满足以下一个或多个条件且业务收益超过运维成本时，可单独部署：

- 客户要求独立网络区、数据驻留、独立密钥或认证边界。
- 负载特征需要独立扩缩容。
- 产品拥有独立 SLA、发布节奏和明确 owner/on-call。
- 多平台复用需求已由稳定 API 证实。
- 合规、数据生命周期或备份恢复要求不同。
- 独立部署收益大于跨服务调用、故障处理和版本兼容成本。

拆分前必须有数据迁移/回滚、API 兼容、故障隔离、授权审计、SLO、备份恢复、升级与成本评估。没有 owner 和运营能力，不进行服务拆分。

## 12. 产品 owner 与运营指标

每个产品需明确产品负责人、技术 owner、发布责任、支持边界和预算/容量责任。指标建议：

| 产品 | 核心指标示例 |
|---|---|
| aiPlat | Agent 发布成功率、治理策略覆盖、资产复用率、授权拒绝正确性、审计完整率 |
| Pi | 安装/升级成功率、Runtime 可用性、任务成功率、断网恢复率、资源使用 |
| 本体 | 模型复用率、映射覆盖/错误率、查询质量、来源可追溯率、数据新鲜度 |
| FDE | 场景到验收周期、需求返工率、证据完整率、验收通过率、交付复用率 |
| 诊断 | 证据覆盖率、关联成功率、评估可复现率、误报/漏报率、问题定位时间 |

指标必须有定义、分母、数据源和责任人。单一总分不得掩盖缺数据或未经行为验收的能力。

## 13. 测试与产品就绪证据

### 单产品行为测试

- **aiPlat**：身份/策略、资产版本、发布、编排、审计、幂等和配额。
- **Pi**：bundle 加载、Runtime 生命周期、离线/在线行为、权限、隔离、升级与回滚。
- **本体**：模型迁移、映射质量、查询授权、来源、新鲜度和回滚。
- **FDE**：项目状态机、客户隔离、方案/任务/验收证据、第三方适配。
- **诊断**：事件关联、评估复现、来源证据、unknown/stale、权限及修复授权。

### 最小跨产品验收路径

1. FDE 创建一个真实业务场景及可测验收目标。
2. FDE 调用本体评估该场景的语义模型/数据准备情况。
3. aiPlat 创建并发布一版 Agent 资产。
4. Pi 在目标环境部署该版本并执行指定任务。
5. Pi/aiPlat 记录运行关联 ID 和版本信息。
6. 诊断接收运行证据，按版本和 trace 形成可复现报告。
7. FDE 根据证据执行客户验收或创建整改任务。
8. 模拟权限拒绝、服务断连、过期数据和升级失败，确认无伪成功。

每条通过结论都应链接到运行日志、测试报告和版本信息。静态文档或 smoke 脚本存在不算行为验收通过。

## 14. ADR 拆分建议

本母稿后续拆成独立决策记录：

1. 五产品职责、非目标与 owner。
2. aiPlat 默认控制面和外部 IAM/控制面 adapter。
3. 产品数据 owner 与跨产品读写规则。
4. Pi Thin/Enterprise Runtime 形态、bundle 与兼容策略。
5. 本体与 Knowledge/RAG 的边界及权威存储。
6. FDE 第一性对象与第三方平台适配。
7. 诊断证据、遥测、报告和修复权限。
8. 独立部署门槛、成本模板和运维责任。

每份 ADR 记录上下文、决策、替代方案、影响、迁移路径、失败回滚条件和重新评估触发条件。

## 15. 明确不预设

- 不预设五产品对应五个仓库、服务或数据库。
- 不把所有身份和业务数据迁入 aiPlat。
- 不把当前 Pi Thin 包等同完整 Enterprise Runtime。
- 不把本体简化为图数据库或 RAG。
- 不把 FDE 扩成通用项目管理套件。
- 不让诊断平台成为超级权限中心或默认自动修复引擎。
- 不把目录、能力行、静态门禁或图谱节点当成生产就绪证据。

## 16. 评审结论

批准方向应理解为：**五个产品域可独立定义和组合；共享能力契约化；先验证真实交付闭环；再按证据决定模块迁移与部署拆分。** 本文是目标架构基线，不是全面搬迁授权或五产品同步开工计划。
