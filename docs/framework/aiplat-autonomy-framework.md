# AI Agent 自主性分级框架

> **体系定位**：以工程化命名定义 AI Agent 自主性阶梯（提示词→上下文→驾驭→循环→元循环），每级对应行业通用标准。适用于任何 AI Agent 系统的自我评估和演进规划。

---

## 1. 框架定位

### 1.1 核心问题

> **它量化的不是智力，而是自主边界。** 核心问题是："你的系统在做决策时，需要多频繁地回头找人类确认？"

不在于"能做什么"，而在于"谁为最终结果负责"——一个接了 50 个工具的 L2 系统，在自治水平上并不比一个只有 3 个工具的 L3 系统更"高级"。

### 1.2 命名体系

本框架采用**工程化命名**（提示词/上下文/驾驭/循环/元循环），每级对应行业通用标准：

| 等级 | 工程名 | 对应通用标准 | 核心引擎类比 | 含义 |
|:---:|------|------|------|------|
| L0 | 无智能 | 无自主 | 脚本 | 基于规则的自动化 |
| L1 | 提示词工程 | 辅助 | Prompt | 写好提示词, 让模型"听懂" |
| L2 | 上下文工程 | 部分自主 | Context | 组装好输入, 让模型"知道" |
| L3 | 驾驭工程 | 条件自主 | Harness | 设计好运行环境, 让模型"靠谱" |
| L4 | 循环工程 | 高自主 | Loop | 让它自己循环跑, 让模型"持续" |
| L5 | 元循环工程 | 完全自主 | Meta-Loop | 系统自己优化自己, 让模型"进化" |

### 1.3 嵌套关系

这些层级不是替代关系，而是**嵌套关系**——Context 包含 Prompt；Harness 组织 Context 并约束执行；Loop 基于 Harness 持续编排任务；Meta-Loop 评估并优化整个系统。

### 1.4 与外部标准的映射

| 本框架 | DeepSeek 定义 | 360 定义 | MIT Index |
|:---:|------|------|:---:|
| L1 提示词工程 | L1 自动补全 | L1 聊天助手 | Chat Agent (L1) |
| L2 上下文工程 | L2 任务执行 | L2 低代码工作流 | Enterprise (设计态 L1-L2) |
| L3 驾驭工程 | L3 多步骤执行 | L3 推理型智能体 | Chat Agent (高端 L3) |
| L4 循环工程 | L4 受限领域全自主 | L4 多智能体蜂群 | Enterprise (部署态 L3-L5) |
| L5 元循环工程 | L5 完全自定议程 | L5 创造其他智能体 | 未达 |

## 2. 六轴评估模型

### 2.1 能力轴定义

| 能力轴 | 简称 | 核心问题 |
|:---|:---|:---|
| **A. 自主性（Autonomy）** | A | 完成一个任务，需要多频繁找人类确认？ |
| **B. 上下文感知（Context Awareness）** | B | 能感知和利用多少信息源？ |
| **C. 工具掌握（Tool Mastery）** | C | 能调用多少工具？如何发现和选择？ |
| **D. 记忆系统（Memory）** | D | 跨会话、跨任务的信息保持能力？ |
| **E. 协作能力（Coordination）** | E | 多 Agent 之间如何通信与分工？ |
| **F. 自进化（Self-Evolution）** | F | 系统能否从执行中学习和优化？ |

### 2.2 最低分原则

> **系统的 L0-L5 等级由六轴中最低分轴决定。** 最薄弱的环节限制整体系统表现。

**为什么不是平均值**：一个"五轴 L5 + 一轴 L2"的系统 ≠ L4.5，而是 L2。因为 L2 轴的那个短板在实际运行中会拖死全局——系统可能生成 L5 级的规划，但执行第一步就因为没有工具调用能力而失败。

**示例**：

| 系统 | A | B | C | D | E | F | 定级 | 原因 |
|:---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:---|
| 系统 X | L5 | L5 | L2 | L5 | L5 | L5 | **L2** | C轴工具只有3个，无法自主执行复杂任务 |
| 系统 Y | L5 | L5 | L5 | L5 | L2 | L5 | **L2** | E轴没有协作能力，多Agent任务无法完成 |
| aiPlat | L5 | L5 | L5 | L5 | L5 | L5 | **L5** | 六轴均衡，无短板 |

> **这就是无法取巧的原因**：宣称"我们是 L5"之前，必须把每一轴都拉到 L5，不是"大多数轴很强就够了"。

### 2.3 跨框架统一决策规则

三框架共享同一决策规则——**最低子项原则**，但每框架的应用方式不同：

| 框架 | 子项含义 | 决策规则 | 一票否决 |
|:---|:---|:---|:--:|
| L1-L5 自主性 | 六轴中每轴的级别 | 最低轴决定整体等级 | 无 |
| 工程落地 | 54 项中每项的 是/否/部分 | 最低维完成度决定整体 | CI/CD 缺失、无自动化测试、无可观测性、无安全扫描、无 ADR |
| 三层企业 | 30 维中每维的 0-5 分 | 最低分层级决定综合 | 不支持私有化部署等 7 项 |

**为什么统一为"最低子项"而非"加权平均"**：

> 加权平均可以掩盖短板——一个维度差 0.5 分，另一个维度好 2 分，加权一平均看不出来。但在实际生产环境中，差的那个维度会单独导致故障。故障不关心你的平均分。

**示例**：系统在 CI/CD 上得分 0/5，在其他维度上全部 5/5。加权平均约 4.7/5——看起来是领导级。但 CI/CD 的缺失意味着不能自动修复 bug，一次上线失败就可能全站宕机。按最低分原则，这个系统是 0/5，初始级——这更接近真实风险。

### 2.4 评估要求

| 要求 | 说明 |
|:---|:---|
| **代码为唯一定论** | 设计文档、ROADMAP、承诺不算数，只有可验证的实现才算 |
| **必须有负检查** | "有 X 能力"必须伴随"没有 Y 能力"的反证 |
| **必须可复现** | 评估结论应可通过命令或测试复现 |

## 3. L0-L5 逐级定义

### L0 — 无智能

> 脚本集合，无 AI 能力。基于正则表达式、定时任务或硬编码规则。

| 轴 | 表现 | 典型特征 |
|:---|:---|:---|
| A | 每步由人类触发 | Shell 脚本 / CI/CD 流水线 / IFTTT |

**人类角色**：全程手动执行。

**升级条件**：规则分支超过 50 条，维护成本超过收益 → 进入 L1。


### L1 — 提示词工程

> 通过精心设计的提示词让模型理解人类意图。所有优化围绕单次对话的文本措辞展开。

| 轴 | 表现 | 通过条件 |
|:---|:---|:---|
| A | 每次由人类输入触发 | LLM 适配器存在 + 提示词模板加载 |
| B | 仅当前对话文本 | — |
| C | 无工具调用 | — |

**人类角色**：任务主导者——负责整合、验证和优化输出。

**升级条件**：需要"记住上次说过什么"或"调用外部工具" → 进入 L2。


### L2 — 上下文工程

> 在有限上下文窗口中构建最优信息环境。核心问题是：**当前到底该给模型哪些信息？**

| 轴 | 表现 | 通过条件 |
|:---|:---|:---|
| A | 人类设定流程，Agent 执行 | RAG 检索器 + 上下文组装器 |
| B | 知识库检索 + 动态信息注入 | Wiki 引擎 + 文档解析器 |
| C | 1-5 个工具，手动选择 | 工具注册表存在 |

**人类角色**：流程设计者——负责管理工作流。

**升级条件**：需要"让 Agent 在边界内可靠执行" → 进入 L3。


### L3 — 驾驭工程

> 构建包裹模型运行的"机械外壳"，确保模型能力在边界内稳定释放。核心问题：**怎样让 Agent 在边界内可靠执行？**

| 轴 | 表现 | 通过条件 |
|:---|:---|:---|
| A | 流程内自主执行 | PolicyGate + ApprovalGate |
| C | 5-20 个工具，自动选择 | SkillRegistry + ToolRegistry |
| — | 安全边界 | SandboxGate 沙箱 |
| — | 基础记忆 | 会话级记忆 (working memory) |

**人类角色**：监督者——监督 Agent 的操作。

**升级条件**：需要"让任务跨轮次持续推进" → 进入 L4。


### L4 — 循环工程

> 构建"行动-观察-评估-修正"的闭环，让 Agent 自主推进复杂业务流程。核心问题：**怎样让任务跨轮次持续推进？**

| 轴 | 通过条件 |
|:---|:---|
| A | 自主重试循环 + HITL 分级配置 |
| B | CRAG 3 级回退 + 本体引擎 (≥23 模块) + RunContext |
| C | 20+ 工具 + MCP 动态发现 |
| D | 四层记忆完整 (working/episodic/semantic/manager) |
| E | Pipeline 多 Agent 编队 (integration.py ≥ 1000 行) |
| F | ErrorTranslator (≥ 19 类) + 自愈策略 (≥ 5) |

**人类角色**：旁观者——仅提供目标和最终评估。

**升级条件**：需要"系统自己优化自己" → 进入 L5。


### L5 — 元循环工程

> 在 Loop 之上再套一层"元循环"——系统不仅执行任务，还会评估执行效果并自动调整优化策略。核心问题：**怎样让这套运行系统持续进化？**

| 轴 | 通过条件 |
|:---|:---|
| A | GoalExecutor 自主闭环 + GoalGenerator 自主提案 |
| B | AdaptiveContextRouter 自学习源选择 + 三档压力自适应 |
| C | ToolBootstrap + handler.py 代码生成 → 部署 → 注册 |
| D | GossipProtocol 推拉分布式同步 + SharedKnowledgePool |
| E | SwarmBroker 合同网协议 + DynamicOrchestrator |
| F | UCB1 策略搜索-评估-比较-回滚闭环 + StrategyTracker + ExecutionSnapshot |

**人类角色**：完全脱离——任何形式的人类参与都不再必要。

## 7. aiPlat 应用实例

### 7.1 评估结论

| 能力轴 | 级别 | 关键证据 |
|:---|---:|------|
| A. 自主性 | **L5** | GoalExecutor 自主闭环 + GoalGenerator 提案 |
| B. 上下文感知 | **L5** | AdaptiveContextRouter 自学习源选择 |
| C. 工具掌握 | **L5** | ToolBootstrap + handler.py 代码生成 |
| D. 记忆系统 | **L5** | GossipProtocol 推拉分布式同步 |
| E. 协作能力 | **L5** | SwarmBroker 合同网协议 |
| F. 自进化 | **L5** | UCB1 搜索-评估-比较-回滚闭环 |

**系统定级：L5 — 元循环工程**

### 7.2 Phase 演变路径

```
Phase 24-28: 自愈 + 快照 + 跟踪 + 共享 + 目标
Phase 29-30: UCB1 搜索 + 自动闭环执行
Phase 31-35: 工具自举 + 动态组队 + handler.py + WAL + LLM分解
Phase 36-38: Gossip + Swarm + AdaptiveContext

39 个 Phase 累积 → 六轴全 L5
```

### 7.3 验证方式

```bash
bash scripts/verify-l4-pyramid.sh      # 结构层 L0→L5 (31 项)
bash scripts/verify-l4-depth.sh        # 能力深度 (30 tests)
```
