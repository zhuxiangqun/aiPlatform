## 一、概述

### 1.1 FDE 是什么

**FDE**（Field Deployment Engineer）是 aiPlat 的客户现场交付方法论。它不是一套点击式的操作流程，而是一个**工程化的交付体系**——定义清楚谁做什么、每步输入什么输出什么、做到什么标准才算完成。

### 1.2 适用场景

| 场景 | 说明 |
|------|------|
| **标准交付** | 客户需求与已有业务域高度匹配，通过 8 步流程直接交付 |
| **新建域交付** | 客户需求无匹配域，需先建域本体、注入种子数据、创建领域 Skill（额外 2-3 天） |
| **标书审查** | 投标阶段快速验证 aiPlat 针对客户场景的可行性，生成技术方案 |
| **POC 快速验证** | 4-6 小时轻量演示，验证方向正确后再决定是否正式交付 |

### 1.3 核心原则

1. **Append-only Pipeline**：每个阶段只写入一个数据键，读取上游键时不可修改。保证数据流向单向、可追溯。
2. **质量门前置**：每个阶段有明确的验收标准，不过关不进入下一阶段。
3. **HITL 审批**：关键产出（客户 Profile、方案设计、验收签收）必须经人工确认。
4. **配置驱动**：Agent 的行为由 AGENT.md 定义，引擎不硬编码业务逻辑。
5. **双模式支持**：自由模式（非标项目）和工作流模式（标准交付）可根据项目类型切换。

### 1.4 FDE 数据安全操作规范

> **适用范围**：所有 FDE 在现场或远程操作期间，涉及客户数据的全生命周期处理。

| 场景 | 安全要求 | 违规后果 |
|------|------|------|
| **客户敏感截图（含 PII/商业机密）** | 截取后须立即打码（至少覆盖姓名、工号、产品图纸编号）。仅允许存储在加密笔记本的 `~/fde_workspace/` 目录，不得上传至个人网盘或公网相册。 | 客户侧安全事件 → 项目暂停 + 合规审查 |
| **本地日志脱敏** | 采集 `logs/` 前必须先运行 `bash scripts/sanitize_logs.sh`（自动替换 IP、用户名、邮箱为 `[REDACTED]`）。脱敏前日志不得带离客户现场。 | 违反 GDPR/个保法 → 法律责任 |
| **airgap 环境数据物理隔离** | 使用专用离线 U 盘（需事先报备），严禁将 airgap 客户的模型文件/本体 YAML 与 online 环境混用。 | 模型泄露 → 合同违约 |
| **U 盘/移动介质操作** | 所有 U 盘必须为硬件加密盘（如 Kingston IronKey），使用前后执行 `sudo shred -vf` 清除残留文件。 | 介质丢失 → 数据外泄 |
| **客户临时账号管理** | 禁止使用客户通用账号（如 root/admin）。需向客户 IT 申请临时个人账号，交付完成后立即注销。 | 审计缺失 → 无法溯源 |

**行前强制检查**（进入步骤①前执行）：
```bash
# 确认本地环境已就绪
./scripts/security_preflight.sh
# 预期输出：✅ 所有安全策略已生效
```

## 二、角色定义

### 2.1 角色总览

FDE 交付团队由 4 个角色组成：

| 角色 | 代号 | Agent 类型 | 核心职责 | 产出物 | Pipeline Key | 文档模板 |
|------|:---:|:---:|------|------|:---:|:---:|
| **业务分析师** | BA | 人工（需客户参与） | 收集客户信息，建立客户 Profile | 客户 Profile | `customer` | [FDE客户档案](templates/template-customer-profile.md) |
| **方案架构师** | SA | AI 自动 + 人工审核 | 匹配业务域，生成诊断报告和方案设计 | 域评估 + 诊断报告 | `domain` + `diagnosis` | [域评估报告](templates/template-domain-assessment.md) · [诊断报告](templates/template-diagnosis-report.md) |
| **交付工程师** | DE | AI 自动 | POC 验证、打包部署、灰度发布 | 部署包 + 灰度报告 | `pocProfile` + `deployVersion` + `canaryResult` | [POC验证报告](templates/template-poc-report.md) · [灰度发布报告](templates/template-canary-report.json) |
| **交付经理** | DM | 人工（需客户签收） | 验收移交、首月护航 | 验收签收 | `adopted` | [交付总结报告](templates/template-delivery-summary.md) · [签收单](templates/template-signoff.md) · [首月护航计划](templates/template-escort-plan.json) |

### 2.2 业务分析师（BA）

**职责边界**：
- 与客户现场沟通，收集企业基本信息
- 识别客户的业务模式、核心痛点、组织关系
- 确认客户的 IT 基础设施和部署环境
- 建立标准化的客户 Profile，作为后续所有步骤的基础数据

**关键决策权**：
- 判断客户信息是否足够进入下一阶段
- 识别是否需要启动多轮澄清（信息模糊、干系人不明确）

**产出物**：客户 Profile（结构化 JSON + 可读 Markdown） → [FDE客户档案模板](templates/template-customer-profile.md)

**对谁负责**：客户负责人、后续步骤的 SA 和 DE

### 2.3 方案架构师（SA）

**职责边界**：
- 根据客户 Profile 匹配最佳业务域
- 运行诊断报告，将客户表层需求翻译为深层业务问题
- 设计解决方案（推荐域、可复用能力、预期效果、缺口评估）
- 评估方案可行性（域成熟度、通过率、数据缺口）

**关键决策权**：
- 判断客户需求与已有域是否匹配（匹配度 <80% 时决定是否先加固域）
- 判断是否需要新建域（额外 2-3 天工时）

**产出物**：诊断报告 + 方案设计（Markdown 格式） → [域评估报告模板](templates/template-domain-assessment.md) · [诊断报告模板](templates/template-diagnosis-report.md)

**对谁负责**：BA（消化客户 Profile）、DE（告知需要构建什么）

### 2.4 交付工程师（DE）

**职责边界**：
- 根据方案设计执行 POC 验证（注入种子数据、测试典型问题）
- 根据部署环境（online/airgap/hybrid）生成离线部署包
- 执行灰度发布，确保上线质量
- 处理环境差异和打包失败等异常

**关键决策权**：
- 判断 POC 验证是否通过（**AI 执行数据注入，FDE 人工判定结果**）→ 须客户技术对接人确认方向正确后才能写入 `pocProfile`
- 判断灰度发布是否可以全量推广
- 发现问题时决定是否回滚

**产出物**：部署包（.zip）+ 灰度报告 → [POC验证报告模板](templates/template-poc-report.md) · [灰度发布报告模板](templates/template-canary-report.json)

**对谁负责**：SA（消化方案设计）、DM（交付可验收的部署包）

### 2.5 交付经理（DM）

**职责边界**：
- 逐项验收 Checklist（功能、KPI、数据、SLA、培训）
- 编写交付手册，组织客户签收
- 启动首月护航计划（4 周持续跟踪）

**关键决策权**：
- 判断交付是否达到签收标准
- 判断是否需要补充培训或文档

**产出物**：交付手册 + 签收单 + 护航计划 → [交付总结报告模板](templates/template-delivery-summary.md) · [签收单模板](templates/template-signoff.md) · [首月护航计划模板](templates/template-escort-plan.json)

**对谁负责**：客户方负责人（最终验收）

## 三、交付模型

### 3.1 双模式选择 — FDE Builder

FDE 提供两种执行方式，适应不同的交付场景：

| | 自由模式 | 工作流模式（FDE Builder） |
|:---|:---|:---|
| **步骤数** | 8 步（FDE 手动切换） | 4 步（4 Agent 按 DAG 自动流转） |
| **执行方式** | FDE 在 8 个 Tab 间自由切换 | BA → SA → DE → DM 顺序流转 |
| **FDE 角色** | 执行者——每个步骤手动操作 | **审核者**——系统自动执行，FDE 审核修正结果 |
| **进度条** | 8 步精细显示 | 4 Agent 显示 |
| **适用场景** | 非标项目、自由探索、临时调整 | 标准交付、团队分工明确 |
| **切换方式** | 默认模式 | 下拉菜单选择工作流 |

> **工作流模式 = FDE Builder**：选中客户后，系统自动串联 4 个 Agent（BA→SA→DE→DM），通过 `run_fde_agent_one_shot()` 完成 60-70% 的交付标准工作（客户 Profile → 域评估 → 诊断报告 → POC 验证 → 交付手册）。FDE 不再需要逐个点击 Tab，只需在关键节点审核确认 AI 的输出结果，必要时补充修正。

### 3.2 八步流水线（自由模式）

```
① 业务认知 → ② 评估域 → ③ 问题重构 → ④ 验证价值 →
⑤ 快速构建 → ⑥ 评测护栏 → ⑦ 验收移交 → ⑧ 运营监控
```

每个阶段的输出通过 Pipeline 传递给下游阶段，上游不可修改下游的写入。

### 3.3 数据传递关系

```
① 选中客户 ──→ ② 评估域 ──→ ③ 问题重构 ──→ ④ 验证价值
     │              │              │              │
     │  industry     │  domain_id   │  diagnosis   │  poc_profile
     ↓              ↓              ↓              ↓
⑧ 监控过滤         ③④ 表单预填   ① 回显 badge   ⑤ 打包输入
```

### 3.4 生态集成层 — 插件化数据源接入

FDE 交付现场的第三方系统（ERP/CRM/MES/IM）对接通过标准化集成插件完成。生态伙伴可独立开发插件并提交到生态市场。

**集成插件规范**（v2.9 启动实现）：

> ⚠️ `BaseIntegrationAdapter` 及插件 SDK 尚未实现。以下为设计规范，当前集成通过 `POST /fde/ingest` + REST API Channel 直接完成。

| 要求 | 说明 |
|------|------|
| 目录结构 | `{name}/plugin.yaml` + `{name}/adapter.py` |
| plugin.yaml | name, version, source_system (ERP/CRM/MES), config_schema |
| adapter.py | 继承 `BaseIntegrationAdapter`，实现 `ingest()` 和 `sync()` |
| 测试 | 附带 `test_adapter.py`，覆盖 connect/ingest/error 三条路径 |

**已有集成能力**：

| 集成类型 | 状态 | 入口 |
|:---|:---:|------|
| SSO/OIDC | ✅ 已实现 | 管理端 → 认证鉴权 → 新增 OIDC Provider（Keycloak/Azure AD/Okta） |
| REST API 集成 | ✅ 已实现 | 渠道管理 → 新建 API 渠道 → 生成 Key → 测试连通 |
| 数据源直连 | ✅ 已实现 | `POST /fde/ingest` — ERP/CRM/MES 字段映射 → 标准 FDE 输入 |
| 企业 IM Webhook | 🔜 待实现 | MCP Webhook 适配器接口已定义（飞书/企微/Slack），代码实现待启动 |
| RBAC 角色同步 | ✅ 已实现 | `permissions.yaml` + JWT 透传 |
| 数据库连接器 | ✅ 已实现 | 平台存储 → 新建连接 → JDBC 自动生成 CRUD 端点 |

> **集成健康监控**：`GET /fde/health` 已包含组件级健康检查。集成插件通过数据源连通性（`curl` 可达）+ 数据新鲜度（最后同步 <24h）+ 错误率（<5%）三项指标上报状态。

### 3.5 客户自助层 — 从委托到自主

客户使用 aiPlat 的方式分三个阶段演进：

| 阶段 | 模式 | 客户角色 | 当前状态 |
|:---:|------|------|:---:|
| **1. 委托模式** | FDE 全权交付 | 客户仅使用，不参与配置 | ✅ **当前** |
| **2. 协作模式** | 客户通过 Builder 对话式调整 Agent 配置 | 客户提议，FDE 审核上线 | ⚠️ v2.8 目标 |
| **3. 自助模式** | 客户在租户空间内自主创建/调整/下线 Agent | 客户自主，平台保障 | vNext |

**当前可用能力**（阶段 1）：

| 能力 | 入口 | 说明 |
|:---|:---|------|
| 终端使用 → 工作台 | `POST /workbench/submit` | 客户可直接提交 AI 任务，无需 FDE 介入 |
| 能力浏览 | `GET /workbench/capabilities` | 客户可见 5 种通用能力 + 行业定制能力 |
| Spec 修订 | `POST /workbench/spec/{id}/revise` | 客户可提出修订请求，系统自动重执行 |
| 效果反馈 | `POST /workbench/tasks/{id}/feedback` | 打分 + 行为信号（复制/重查/放弃）→ FeedbackRadar |
| KPI 仪表板 | Value → KPI 管理 | 客户可自行设定和查看 KPI |

> **协作模式路线图**（v2.8）：客户通过 Builder 对话式修改 Agent SOP（如增加质检行业规则），系统生成修订 Spec → FDE 审核 → 一键上线。详见 `04-fde-admin.md`。

### 步骤 ①：业务认知

**目标**  
    建立客户的标准化 Profile，为后续所有步骤提供基础数据。

**负责角色**：BA（业务分析师）

**前置输入**  
    无。这是整个流程的第一步。

**过程活动**  
    1. 与客户现场访谈，收集五类信息：
       - **企业身份**：公司全称、所属行业、组织规模
       - **业务模式**：做什么、挣什么钱、核心流程
       - **痛点**：当前业务中 AI 最相关的瓶颈环节
       - **技术基础**：IT 基础设施、是否可访问外网（决定部署模式）
       - **组织与合规**：决策者是谁、谁会配合、谁可能阻力、合规要求
    2. 判断部署模式：online / airgap / hybrid
    3. LLM 自动推断行业分类（如"智能锁安装"→ 安装服务行业）
    4. 信息不全时启动多轮澄清
5. 若 AI 自动匹配的域置信度低于 80% 或明显错误，FDE 可**手动修正**：
   - 点击业务领域旁的 **[✎ 手动选择]** → 在弹窗中搜索目标域关键词 → 选择正确的域 → 系统弹窗确认覆盖原因（必填，如 "AI 误判为 finance，实际为 supply-chain"）
   - 覆盖记录写入 `pipeline.domain.override_reason`，供后续审计追溯

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|
| [`FDE客户档案_{客户名}.md`](templates/template-customer-profile.md) | Markdown | 客户全称、行业、业务模式、核心痛点、IT 基础与部署模式、组织关系 | 后续所有步骤的输入 |
| `customer`（Pipeline） | JSON | 结构化数据：`name`、`industry`、`namespace`、`deploy` | ②③⑧ 自动读取 |

**验收标准**  
     - 能用 3 句话说清客户"做什么、挣什么钱、卡在哪里"
    - 组织关系已绘制（知道谁拍板、谁配合、谁可能阻力）  
    - 部署模式已确认（直接问客户：生产环境能不能访问外网）

**典型耗时**：0.5–1 天（含客户现场访谈）

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 客户信息不完整 | 启动多轮澄清追问，直到信息完整 |
| 客户拒绝提供某些信息 | 标记为"待补充"，后续步骤在相关环节需特别关注 |
| 部署模式无法当场确认 | 默认按 airgap 准备（最严格），后续可修正 |

### 步骤 ②：评估域

**目标**  
    评估 aiPlat 的能力资产中哪些可以复用，哪些需要从零建设。

**负责角色**：SA（方案架构师）

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|
| `FDE客户档案_{客户名}.md` | Markdown | 步骤① | 客户行业、业务描述、痛点 |

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|
| [`域评估报告_{客户名}.md`](templates/template-domain-assessment.md) | Markdown | 匹配域列表、成熟度评分、已选择的目标域、已知缺口清单 | ③ 诊断输入、决策参考 |
| `domain`（Pipeline） | JSON | 结构化数据：`id`、`maturity`、`gaps` | ③④ 自动传入 |

**验收标准**  
    - 已选定目标域（如"供应链"或"采购管理"）  
    - 域的通过率已评估  
    - 已知缺口已被理解（哪些缺口影响交付、哪些可以绕过）

**典型耗时**：5–15 分钟

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 无匹配域 | 新建域本体 → 种子数据注入 → 创建领域 Skill（+2-3 天） |
| 匹配域通过率 <60% | 补充种子数据 + 优化本体定义后再评估 |
| 匹配域通过率 60-80% | 可进入 ③，但在方案设计中标注风险 |

**下一阶段**：→ 步骤 ③

### 步骤 ③：问题重构

**目标**  
    将客户的表层需求翻译为真实的深层业务问题。

**负责角色**：SA（方案架构师）

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|
| `FDE客户档案_{客户名}.md` | Markdown | 步骤① | 客户行业、业务描述 |
| `域评估报告_{客户名}.md` | Markdown | 步骤② | 选定域 ID、成熟度、已知缺口 |

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|
| [`诊断报告_{客户名}.md`](templates/template-diagnosis-report.md) | Markdown | 深层问题、推荐域、已知缺口、方案路线图 | ④ POC 输入、方案设计的核心依据 |
| `diagnosis`（Pipeline） | JSON | 结构化数据：`deep_problem`、`domain` | ④⑦ 自动传入、① 回写 |

**验收标准**  
     - 诊断报告中的"深层问题"与客户最初说的不一致（说明翻译成功）
    - 报告引用了具体域的通过率和已知缺口  
    - 客户确认深层问题才是真痛点

**典型耗时**：15–30 分钟（含客户确认环节）

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 客户不认同诊断结论 | 回到 ① 补充信息后重新诊断 |
| 诊断无法匹配深层问题 | 提交反馈，标记为知识缺口 |
| 域数据不足以支撑诊断 | 回到 ② 加固域数据 |

**下一阶段**：→ 步骤 ④

---

### 步骤 ④：验证价值

**目标**  
    用最小成本（POC）验证"这个方向值不值得做"。

**负责角色**：DE（交付工程师）

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|
| `域评估报告_{客户名}.md` | Markdown | 步骤② | 域 ID、成熟度 |
| `诊断报告_{客户名}.md` | Markdown | 步骤③ | 深层问题、推荐域 |

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|
| [`POC验证报告_{客户名}.md`](templates/template-poc-report.md) | Markdown | 测试问题列表、回答正确率、错误记录、客户确认结论 | ⑤ 打包输入、决策参考 |
| `pocProfile`（Pipeline） | JSON | 结构化数据：`accuracy`、`errors` | ⑤ 自动传入 |

**HITL 判定节点**（步骤④独有的强制人工闸门）：
- POC 测试完成后，DE 现场向客户技术对接人展示 3 个典型问题结果
- 客户必须明确口头或书面确认："这个方向是对的" → 记录原话 → 写入 `pocProfile.customer_approval_quote`
- 若客户不认可 → 标记 `pocProfile.status = "rejected"`，禁止自动流入步骤⑤，强制回到步骤③重新诊断

**验收标准**  
     - ≥2/3 典型问题回答正确
    - 客户明确表示"方向是对的"  
    - 已知错误和改进点已记录并提交反馈

**典型耗时**：2–4 小时（含客户验证）

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| ≥2/3 回答错误 | 回到 ② 加固域数据，补充种子 |
| 正确但客户不认可方向 | 回到 ③ 重新诊断 |
| 问题超出预期范围 | 提交反馈 → 重新评估 → 可能需要新建域 |

**下一阶段**：
    - POC 通过 → 步骤 ⑤
    - POC 失败 → 回到 ② 或 ③

### 步骤 ⑤：快速构建

**目标**  
    将 POC 验证通过的方案打包为标准化的离线部署包。

**负责角色**：DE（交付工程师）

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|
| `POC验证报告_{客户名}.md` | Markdown | 步骤④ | POC 验证结果、正确率 |
| `FDE客户档案_{客户名}.md` | Markdown | 步骤① | 部署模式（online/airgap/hybrid） |

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|
| `部署包_{客户名}_{版本}.zip` | ZIP | 域本体 YAML、Wiki 数据、GraphIndex、Skill 定义、部署配置、install.sh | ⑥ 灰度发布安装包 |
| `deployVersion`（Pipeline） | string | 版本号 | ⑥ 灰度版本标识 |

**过程活动**  
    1. 收集部署包内容：
       - 域本体 YAML 定义（`~/.aiplat/ontologies/`）
       - Wiki 页面数据（对应 collection）
       - GraphIndex 图数据（SQLite）
       - 相关 Skill 定义（SKILL.md）
       - 部署配置（JSON）
     2. 如果部署模式为 airgap，打包时需要包含 LLM 模型文件（包体积大 50-80 倍）
     3. **hybrid 与 airgap 打包差异**：
        - airgap：必须打包完整 LLM 模型文件（无网络），包体积大 50-80 倍，且需现场物理安装
        - hybrid：模型可选择打包（若内部网关无法稳定访问云端 API），也可走网关代理（若网络策略允许白名单）；包体积可配置，比 airgap 灵活
        - FDE 在 ① 中确认部署模式后，打包脚本自动适配；若现场发现网络策略与预期不符，允许在⑤打包前重新修改 `customer.deploy`（须备注变更原因）
     4. 生成 .zip 部署包
     5. 传输到客户环境 → 解压 → 运行安装脚本

> **部署模式对评分的影响**：`online/airgap/hybrid` 不仅决定打包内容，还会在后台影响解决方案的可行性评分（`ontology_bus.py` 中 airgap 约束会触发额外的本地推理评分项）。打包前可通过 `/fde/score` 预览不同模式下的方案评分差异。



**验收标准**  
    - 部署包生成成功（有下载链接）  
    - 客户环境安装完成（安装脚本无报错）  
    - 核心功能可用（在客户环境能跑通 POC 典型问题）

**典型耗时**：10–30 分钟（打包 + 传输 + 安装）

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 打包失败 | 检查部署日志：常见原因包括端口占用 → 修改映射；脚本报错 → 检查 install.sh |
| airgap 包过大 | 确认是否必须包含模型文件，online/hybrid 环境可去除模型 |
| 安装脚本报错 | 逐行排查 install.sh 日志，常见是 Python 依赖或端口冲突 |

**下一阶段**：→ 步骤 ⑥

### 步骤 ⑥：评测护栏

**目标**

**负责角色**：DE（交付工程师）

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|

**过程活动**

    2. 开启灰度：初始 5-10% 流量 → 观察 10-30 分钟

**典型耗时**：30 分钟–2 小时（取决于灰度阶段数和观察时间）

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 质量指标显著下降 | 一键回滚到上一版本，修复后重新灰度 |
| 发现新的高影响 bug | 回滚 → 定位问题 → 修复 → 重新灰度 |
| 回滚失败 | 手动切回旧版本 → 排查回滚失败原因 |

**负责角色**：DM（交付经理）

**过程活动**

       - 第 1 周：确认无阻塞问题
       - 第 2 周：检查运营监控面板
       - 第 3 周：收集客户反馈
       - 第 4 周：首月总结 → 进入稳定运营




**验收标准**  
    - Checklist 全部通过（所有框打勾）  
    - 客户签收单已签字  
    - 首月护航已激活

**典型耗时**：签字 30 分钟，护航持续 4 周

**异常处理**  
| 异常 | 处理方式 |
|------|------|
| 签收卡在某个审批人 | 识别卡点 → 提供替代方案 → 升级处理 |
| 培训效果不达标 | 增加实操环节，提供录制视频辅助 |

### 步骤 ⑧：运营监控

**目标**  
    交付后持续跟踪，确保系统运行稳定。"做完不算完，用起来才算"。

**负责角色**：DM（交付经理）+ 自演进系统

**输入文档**
| 文档名称 | 格式 | 来源 | 内容描述 |
|------|------|:---:|------|
| `FDE客户档案_{客户名}.md` | Markdown | 步骤① | 客户 namespace（监控过滤键） |
| `首月护航计划_{客户名}.json` | JSON | 步骤⑦ | 健康检查调度配置 |

**输出文档**
| 文档名称 | 格式 | 内容描述 | 用途 |
|------|------|------|------|

| [`月报_{客户名}_{月份}.md`](templates/template-monthly-report.md) | Markdown | 月度趋势分析、知识积累总结 | 季度复盘、客户汇报 |

**过程活动**

       - 自演进知识原子数（期望持续增长）

       - 修复层：已知模式自动修复（confidence ≥0.9）
       - 演化层：从知识缺口发现新术语和新方案



**验收标准**  
    - 移交后验收结束（客户已打回访电话或邮件确认）  
    - 未出现新问题（无新增阻塞 alerts）  
    - 准备下一个客户（已回到步骤 ①）

**典型耗时**：每次 2-5 分钟，持续进行

| | `canaryResult.passed` | bool | ⑥ | ⑦ | 灰度是否通过 |
| `交付总结报告_{项目名}.pdf` | `adopted` | bool | ⑦ | ⑧ | 是否已验收签收 |

> 以上为文档逻辑命名，便于阅读。代码实际使用的物理 Key 为蛇形原子粒度，对照如下：

| 文档逻辑名 | 代码物理 Key（蛇形） | 粒度 | 备注 |
|------|------|:---:|------|
| `customer` | `customer_name`, `customer_industry`, `customer_namespace`, `customer_desc`, `customer_deploy` | 5 个 | `customer_desc` 为富文本描述字段 |
| `domain` | `domain_id`, `domain_maturity`, `domain_skills` | 3 个 | `domain_skills` 为 Skill 计数值（int） |
| `diagnosis` | `diagnosis_deep_problem`, `diagnosis_domain` | 2 个 | 全量报告（`diagnosis_full_report`）不在 pipeline_state 中，单独存储 |
| `pocProfile` | `poc_profile`（模板名 string） | 1 个 | **vNext** 将拆分为 `poc_accuracy`, `poc_errors`, `poc_customer_approved` 原子键 |
| `deployVersion` | `deploy_version` | 1:1 |
| `canaryResult` | `canary_passed`, `canary_score` | 2 个 | **vNext** 将增加 `canary_rollback_count` |
| `adopted` | `adopted`（bool） | 1:1 |

> **vNext 路线图说明**：`pocProfile` 和 `canaryResult` 的原子化拆分已列入规划。当前代码保持向后兼容，新增原子键为增量字段，不影响旧 `pipeline_state` 数据。

### 5.2 读写规则

- 每个步骤只**写入**一个主键
- 读取上游键时 **UI 层面提供读写校验提示**（`collected_vs_expected`），显示各步骤的预期产出 vs 实际产出
- 实际运行时强制拦截为 vNext 路线图，当前交付依赖 FDE 操作规范和 Code Review 保障数据完整性
- 步骤跳过时，该步骤的写入键**保持为空**，下游需做空值检查

## 七、质量保障

### 7.1 各阶段质量门

| 阶段 | 质量门 | 通过标准 | 不通过处理 |
|:---:|------|------|------|
| ① | 客户信息完整性 | 五类信息齐全 | 启动多轮澄清 |
| ② | 域匹配度 | 通过率 ≥80% | 加固域或新建域 |
| ③ | 诊断有效性 | 深层问题 ≠ 表层需求 | 补充信息后重新诊断 |
| ④ | POC 正确率 | ≥2/3 问题正确 | 加固域数据 |
| ⑤ | 部署包可用性 | 安装脚本无报错 | 检查日志修复 |
| ⑥ | 灰度质量 | 质量指标无显著下降 | 回滚到旧版本 |
| ⑦ | 验收 Checklist | 全部通过 | 逐项修复后重新验收 |

### 7.2 HITL 审批点

| 审批关卡 | 所在步骤 | 审批人 | 触发时机 | 流转条件 |
|------|:---:|------|------|------|
| `customer_profile_review` | ① | BA + 客户负责人 | 客户 Profile 完成后 | 干系人确认信息准确 |
| `poc_result_review` | ④ | DE + 客户技术对接人 | POC 测试完成后 | 客户明确确认方向正确（引用原话） |
| `solution_review` | ③ | SA + 技术负责人 | 方案设计完成后 | 技术方案评审通过 |
| `signoff_approval` | ⑦ | DM + 客户负责人 | Checklist 全部通过后 | 签收单签字 |

### 7.3 回退策略

| 回退场景 | 操作 | 影响 |
|------|------|------|
| ⑥ 灰度发现问题 | 一键回滚到旧版本 | 无影响，恢复原状 |
| ③ 客户不认同诊断 | 回到 ① 重新收集信息 | 增加 0.5-1 天 |
| ② 域不匹配 | 加固域数据后重新评估 | 增加 1-2 天 |
| ② 无匹配域 | 新建域本体 + 种子数据 | 增加 2-3 天 |

### 7.4 项目中止与归档（非正常终止）

当交付无法继续时，须执行标准中止流程，避免"烂尾项目"无迹可寻。

**触发场景**（满足任一即可启动中止流程）：

| 场景 | 判定标准 | 示例 |
|------|------|------|
| POC 反复失败 | 同一客户在步骤④重试 ≥3 次，且正确率始终 < 50% | 客户数据质量极差，无法清洗 |
| 预算/合同中断 | 客户方明确告知项目暂停或取消（邮件/书面为证） | 客户被收购，IT 预算冻结 |
| 客户主动退出 | 客户方签字确认终止合作 | 客户选择竞品方案 |

**中止归档步骤**：

1. **快照冻结**：立即对当前 pipeline state（含已填写的 `customer`、`domain`、`diagnosis`）执行 `POST /fde/project/freeze`，生成只读归档包 `{客户名}_aborted_{日期}.zip`。
2. **资产清理**（按 §1.4 安全规范执行）：
   - 删除客户环境中的所有临时账号
   - 回收本地所有未脱敏日志（`shred -vf logs/*`）
   - 加密交付物（如已打包的部署包）移入内部长期存档，客户侧不留副本
3. **客户告知**：输出 `项目中止告知函_{客户名}.pdf`（含中止原因、已交付资产清单、数据销毁声明），由 DM 和客户负责人双方签字存档。
4. **内部复盘**：在中止后 5 个工作日内完成 Retrospective 报告，归档至交付管理后台。

**状态标记**：Pipeline 最终状态标记为 `aborted`，不再流转至后续步骤。

### 7.5 交付范围变更流程（Scope Change）

当客户在步骤④-⑦期间提出**超出诊断报告范围**的新需求时，走标准变更流程，而非默认"一律接受"或"一律拒绝"。

**触发条件**（满足任一）：
| 条件 | 示例 |
|------|------|
| 需求超出诊断报告 §5 "Top 3 机会" 定义的范围 | 原定只做质检报告 OCR，客户要求增加供应商财务风险评估 |
| 需求需要新建域本体或领域 Skill | 客户行业从"制造"扩展到"物流"，需新建 `logistics` 域 |
| 需求导致预估工时增加 ≥20% | 原定 8 人天，新增需求预估 +3 人天 |

**变更流程**：

| 步骤 | 操作 | 负责 | 产出 |
|:---:|------|:---:|------|
| 1 | **影响评估**：DE 评估新需求对域本体、Skill、部署包、SLA 的工时和质量影响 | DE | 变更影响评估（口头/书面） |
| 2 | **变更记录**：在 ⑧ 运营监控提交"变更请求"，注明原因、预估工时、对原验收标准的影响 | DE | 变更请求记录 |
| 3 | **客户确认**：DM 向客户发送变更影响评估，客户书面（邮件/签章）确认后方可继续 | DM | 客户确认凭证 |
| 4 | **归档跟踪**：变更记录归入交付总结报告 §八"已知遗留问题"，或明确标注为"二期规划"（如变更过大的话） | DM | 归档记录 |

**费用/合同影响**：
- 若变更导致工时增幅 <10%：默认吸收，不额外收费
- 若变更导致工时增幅 ≥10%：需走商务变更流程（不在本交付流程范围内），由 DM 协调商务团队处理
