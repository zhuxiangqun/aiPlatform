# FDE 交付操作手册

> ← [文档导航](README.md)

> **目标角色**：日常 FDE 交付工程师  
> **前置条件**：已完成[快速入门](./01-fde-quickstart.md)  
> **访问地址**：`http://localhost:5173/diagnostics` → 点击 "FDE Dashboard"

---

## 一、概述

FDE 工作台按 **八步交付流程** 组织，覆盖从"了解客户"到"运营监控"的完整链路。

### 八步流程（Append-only Pipeline）

```
① 业务认知 → ② 评估域 → ③ 问题重构 → ④ 验证价值 →
⑤ 快速构建 → ⑥ 评测护栏 → ⑦ 验收移交 → ⑧ 运营监控
    ↓ 选客户           ↓ 选域               ↓ 诊断完成
    传给 ② ⑧          传给 ③ ④            回显到 ①
```

**核心机制**：八个 Tab 通过 Append-only Pipeline 串联。每个 Tab 只写入一个 key，读取上游 key 时不可修改。Tab 栏上方有流程进度指示条——各步骤标注 Tab 编号（`客户 ① → 域 ② → … → 监控 ⑧`），已完成显示绿色 ✓，当前所在蓝色高亮，未开始为灰色。

### Agent 与 Skill 对应表

| 步骤 | Tab | 进度条 | Agent | Skill | 写入 | 读取上游 |
|:---:|------|:---:|------|------|:---|:---|
| ① | 业务认知 | `客户 ①` | 业务分析师 | `customer_profile_creator` | `customer` | — |
| ② | 评估域 | `域 ②` | 方案架构师（后台自动匹配） | `domain_assessor` | `domain` | `customer.industry` |
| ③ | 问题重构 | `诊断 ③` | 方案架构师 | `domain_assessor`, `field_assessment` | `diagnosis` | `domain.id` |
| ④ | 验证价值 | `POC ④` | 交付工程师（AI执行注入 + FDE人工判定结果） | `poc_data_inject` | `pocProfile` | `domain` |
| ⑤ | 快速构建 | `部署 ⑤` | 交付工程师 | `package_builder` | `deployVersion` | `pocProfile`, `customer.deploy` |
| ⑥ | 评测护栏 | `灰度 ⑥` | 交付工程师 | `canary_runner` | `canaryResult` | `deployVersion` |
| ⑦ | 验收移交 | `验收 ⑦` | 交付经理 | `acceptance_checker`, `manual_generator` | `adopted` | `canaryResult`, `diagnosis`, `customer` |
| ⑧ | 运营监控 | `监控 ⑧` | 交付经理（持续运维） | — | — | `customer.namespace`, `adopted` |

> **AI 澄清引擎**（`_clarify()`）为系统内置能力，无需注册为 Skill。当 FDE 在任意步骤提交反馈时自动触发多轮对话澄清，帮助定位阻塞根因。详见 [本文 §五](#五反馈机制ai-澄清引擎)。

### 双模式支持 — FDE Builder

FDE 工作台提供两种执行方式。**工作流模式即 FDE Builder**：选中客户后系统自动串联 4 个 Agent，完成 60-70% 的交付标准工作，FDE 只需在关键节点审核结果。

| 模式 | 如何切换 | 进度条格式 | 适合场景 |
|:---|:---|:---|:---|
| **自由模式**（默认） | 下拉选 "自由模式" | `客户 ① → 域 ② → … → 监控 ⑧`（8 步） | 非标交付，FDE 手动切换 Tab |
| **工作流模式（FDE Builder）** | 下拉选 "FDE 标准交付 v1" | `BA ① → SA ②③ → DE ④⑤⑥ → DM ⑦⑧`（4 步） | 标准交付，Agent 自动流转，FDE 审核确认 |

> 工作流模式详见 [本文 §六](#六工作流模式多-agent-协作)。

### 贯穿能力

- **🟡 反馈按钮**（右下角浮动）：任意步骤中点击，即时提交现场反馈。自动关联当前步骤，汇总到运营监控面板。
- **AI 澄清引擎**：反馈不再是固定表单，而是多轮对话澄清。详见 [本文 §五](#五反馈机制ai-澄清引擎)。

## 二、各步骤详细操作

### ① 业务认知 — 了解客户

**目标**：进场第一件事。了解客户的业务模式、关键流程，而不只是看技术需求。

**操作**：

1. 进入 ① Tab → 查看已有客户 Profile 列表（卡片网格布局）
2. **新建客户**：点击右上角 **[+ 新建]** → 填写表单：
   - 客户名称（必填）、命名空间（选填）、描述（选填）
   - 部署模式（online / airgap / hybrid）
3. **展开详情**：点击卡片 → 查看健康数据、MCP 数量、[切换至此] / [删除]
4. **切换 Profile**：后续所有操作自动带上该客户上下文
5. **编辑 Profile**：展开后点击 [编辑] → 可修改名称、描述、部署模式
6. 选中客户后系统自动通过 LLM 推断行业（如"智能锁安装"→ 安装服务）

**Pipeline 连接**：

```
① 选中客户 → customer 写入 pipeline
    ├→ ② 评估域：industry 用于高亮匹配的域
    ├→ ⑧ 运营监控：namespace 用于过滤监控指标
    └→ ① 回显：③ 诊断完成后，客户卡片显示蓝色诊断摘要 badge
```

**"切换" 的含义**：切换后，④ POC 模板绑定到该客户 namespace、③ 诊断上下文自动关联该客户、⑧ 运营监控按该客户过滤指标。

**部署模式说明**（影响后续打包和灰度）：

| 模式 | 含义 | 打包影响 | 灰度影响 |
|:---|:---|:---|:---|
| **online** | 可访问外网，模型走云端 API | 只打包 YAML + wiki + Skill | 可远程滚动更新 |
| **airgap** | 完全断网（政务内网/军工） | 含模型文件（包大 50-80 倍） | 须现场替换 |
| **hybrid** | 有内部网关，不能直连公网；可通过内部网关/代理访问外部 API，模型可打包也可走网关代理（比 airgap 灵活） | 模型打包，代理连数据源；**允许配置不使用本地模型而走网关代理** | 内网网关分发 |

> **判断方法**：直接问客户——"生产环境能不能访问外网？"不能 → 追问是全部不能（airgap）还是有网关（hybrid）。

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 客户业务模式明确 | 能用 3 句话说清客户"做什么、挣什么钱、卡在哪里" |
| 客户关键流程已知 | 知道哪个环节的痛点和 AI 最相关 |
| 组织关系清晰 | 知道谁能拍板、谁会配合、谁可能产生阻力 |

**典型耗时**：进场后 0.5–1 天（含客户现场访谈）。

---

### ② 评估域 — 看能力边界

**目标**：评估 aiPlat 哪些能力可复用，哪些需从零建设。

**Pipeline 连接**：接收 ① 传入的客户行业，自动高亮匹配的业务域。

**操作**：

1. 切换到 ② Tab
2. 系统自动匹配客户行业 → 显示绿色边框 + 🟢"推荐"标签：
   - **制造业** → supply-chain、ship-design、it-ops 高亮
   - **金融业** → finance、procurement-mvo 高亮
   - **零售业** → supply-chain、procurement-mvo 高亮
3. 点击域卡片 → 展开详情 + 写入 pipeline → 传递给 ③ ④

**决策场景**：

| 场景 | 动作 |
|:---|:---|
| 客户需求与已有域高度匹配（如 supply-chain `building` 级别） | → 直接进入 ③ |
| 部分匹配但通过率 <80% | 先加固域数据（打开 /infra/ontology（本体模型） → "🔧 修复"），再进入 ③ |
| 无匹配域 | 新建域本体 → 种子数据 → 域 Skill（额外 2–3 天） |

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| Pipeline 中 domain 已设置 | 进度条 "域" 显示绿色 ✓ |
| 域在 ③ 中自动填入 | 切换到 ③ → "业务领域" 已预填 |
| 域成熟度被评估 | 知道了通过率、实体数、Skill 可用性 |
| 已知缺口被理解 | 知道哪些缺口影响交付，哪些可绕过 |

**典型耗时**：5–15 分钟。

---

### ③ 问题重构 — 诊断真问题

**目标**：把客户的表层需求翻译为真实的业务问题。

**Pipeline 连接**：接收 ② 传入的域 ID，自动填入"业务领域"字段。诊断完成后将结果回写到 ① 客户卡片。

**操作**：

1. 切换到 ③ Tab → "业务领域"已自动填入（如 `supply-chain`），不可手动覆盖。若 AI 匹配明显错误，可手动修正：
   - 点击业务领域字段旁的 **[✎ 手动选择]** → 弹窗显示候选域列表（按匹配度排序）
   - 选择正确域 → 弹窗强制填写"覆盖原因"（例如："AI 误判为金融服务，实际应为供应链"）
   - 确认后系统记录 `domain.override_reason`，覆盖记录可通过 ⑧ 运营监控的审计日志查看
2. 填写诊断表单 → 点击**运行诊断**
3. 诊断完成后：报告展示在右侧面板、自动提取"深层问题"和"推荐域"写入 pipeline
4. 切回 ① → 展开客户卡片 → 底部出现蓝色诊断摘要 badge

**Pipeline 回写**：

```
③ 诊断报告生成
    ├→ diagnosis 写入 pipeline（深层问题 + 推荐域 + 报告全文）
    ├→ 进度条 "诊断" 显示绿色 ✓
    └→ ① 客户卡片：蓝色 badge 显示最近诊断摘要
```

**核心原则**：

> 每接到一个需求，连续追问几次"为什么"。  
> "我要知识库" → "为什么需要知识库？" → "老专家快退休了" → "真正的问题是经验传承"。

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 表层需求被翻译为深层问题 | 诊断报告中的"深层问题"与客户最初说的不一样 |
| 方案有本体域背书 | 报告引用了具体域的通过率和已知缺口 |
| 客户确认深层问题才是真痛点 | 老板可以说"对，我就是担心老张走了没人能接手" |

**典型耗时**：15–30 分钟（含客户确认）。

---

### ④ 验证价值 — 快速 POC

**目标**：用最小成本验证"这件事值不值得做"。

**操作**：

1. 切换到 ④ Tab → 从行业模板中选择（制造业/金融/零售/通用）
2. 点击**加载模板** → 系统自动切换 Profile
3. 点击**快速数据注入** → 自动调用 `poc_data_inject` Skill 注入种子数据
4. 在 Chat 面板测试 2–3 个典型问题 → 验证 ≥ 2/3 正确 → 记录错误和改进点

**决策门槛**：

| POC 结果 | 下一步 |
|:---|:---|
| ≥ 2/3 正确，客户认可 | → ⑤ 快速构建 |
| 正确但客户不认可方向 | → 回到 ③ 重新诊断 |
| ≥ 2/3 回答错误 | → 回到 ② 加固域数据 |
| 问题超出预期范围 | → 提交反馈 → 重新评估 |

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 核心链路已跑通 | ≥ 2/3 典型问题回答让客户认可 |
| 客户确认价值 | 客户明确表示"方向是对的" |
| 已知问题已记录 | 错误和改进点已通过反馈按钮提交 |

**典型耗时**：2–4 小时（含客户验证）。

---

### ⑤ 快速构建 — 打包部署

**目标**：把 POC 验证通过的方案打包为离线部署包。

**操作**：

1. 切换到 ⑤ Tab → 点击**开始打包**
2. 后台异步执行（30s–2min），打包内容：
   - 域本体 YAML（`~/.aiplat/ontologies/`）
   - Wiki 页面数据（对应 collection）
   - GraphIndex 数据
   - 相关 SKILL 定义
   - 部署配置 JSON
3. 打包完成后显示**下载链接**
4. 传输 `.zip` 到客户环境 → 解压运行安装脚本

**注意事项**：
- airgap 环境需包含 LLM 模型文件
- 打包前确认种子数据已注入（② Tab 确认域状态为"构建中"或"生产就绪"）
- 打包失败时检查部署日志

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 部署包生成成功 | 有下载链接 |
| 客户环境安装完成 | 安装脚本无报错 |
| 核心功能可用 | 客户环境能跑通 POC 典型问题 |

**典型耗时**：10–30 分钟（打包 + 传输 + 安装）。

---

### ⑥ 评测护栏 — 灰度发布

**目标**：上线前最后防线——确保 Demo 能跑 ≠ 生产可用。

**操作**：

1. 切换到 ⑥ Tab → 查看灰度状态（当前版本、流量策略、质量指标）
2. 上线新版本：
   - 内部部署新版本 → 点击**开启灰度** → 初始 5–10% 流量
   - 观察 10–30 分钟：错误率、回答质量、用户反馈
   - 逐步提升：30% → 50% → 100%
3. **发现问题**：点击**一键回滚** → 输入回滚原因 → 流量切回旧版本 → 提交反馈

**质量指标说明**：

| 指标 | 含义 |
|------|------|
| 忠实度 | 回答是否基于检索到的文档（幻觉率） |
| 回答相关度 | 回答与问题的语义距离 |
| 检索精度 | 检索到的文档与问题匹配度 |

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 灰度发布完成 | 100% 流量在生产环境运行，无回滚 |
| 质量指标稳定 | Golden Query 通过率未显著下降（<5%） |
| 无重大投诉 | 运营监控中无新的 `high` 严重度告警 |

**典型耗时**：30 分钟–2 小时。

---

### ⑦ 验收移交 — 客户签收

**目标**：系统上线 ≠ 被采纳。确保客户真正使用系统。

**操作**：

1. 切换到 ⑦ Tab → 逐项检查 Checklist：

| Checklist | 验证方式 |
|:---|:---|
| 功能符合诊断报告定义的范围 | 与客户逐项确认 |
| Key User 完成操作培训 | 培训记录签字 |
| 生产环境稳定运行 ≥ 24 小时 | 运营监控无 critical 告警 |
| 典型问题正确率 ≥ 80% | Golden Query 评测 |
| 客户确认签收 | 签收单签字 |

2. 点击**移交归档** → 生成交付总结报告（诊断 + POC + 部署 + 评测）
3. 点击**首月护航** → 启动 30 天自动健康检查

**移交后职责**：

| 阶段 | 动作 | 频率 |
|:---|:---|:---|
| 移交时 | 完成 Checklist + 签收 | 一次 |
| 第 1 周 | 联系客户，确认无阻塞 | 一次 |
| 第 2 周 | 检查运营监控面板 | 一次 |
| 第 3 周 | 收集客户反馈 | 一次 |
| 第 4 周 | 首月总结 → 进入稳定运营 | 一次 |

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| Checklist 全部完成 | 所有框打勾 |
| 客户签收 | 签收单已签字 |
| 首月护航已启动 | 护航计划被调度器激活 |

**典型耗时**：签字 30 分钟，首月护航持续 4 周。

---

### ⑧ 运营监控 — 持续护航

**目标**："做完不算完，用起来才算"。

**操作**：

1. 切换到 ⑧ Tab
2. 查看核心指标仪表盘
3. 查看自演进系统状态（详见 [03 - 运维与自演进](./03-fde-operations.md)）

**判断标准**：

| 完成了吗？ | 信号 |
|:---|:---|
| 移交后验收结束 | 客户打了回访电话或邮件确认 |
| 未出现新问题 | 运营监控无新增阻塞 alerts |
| 准备下一个客户 | 你已经回到 ① 选择新的客户 Profile |

## 三、快速决策矩阵

当你在某个步骤卡住时，参考下表：

| 卡住原因 | 解决 |
|:---|:---|
| 不知道从哪里开始 | ① 选客户，跟着进度条走 |
| 客户不存在 | ① → [+ 新建] 创建 Profile |
| 没有匹配的域高亮 | 确认 ① 中客户行业已正确设置 |
| "业务领域"未预填 | 确认 ② 中已点击选中域卡片 |
| 诊断报告未回显到 ① | 诊断完成后切回 ① → 展开客户看蓝色 badge |
| POC 回答准确率低 | ② 加固域数据（打开 /infra/ontology（本体模型） → "🔧 修复"） |
| 客户不认可方案 | ③ 重新诊断 |
| 客户是 airgap 环境 | 确认 ⑤ 打包清单包含模型文件 |
| 质量指标下降 | ⑥ 回滚到上一版本 |
| canaryResult 未传递 | 确认 ⑥ 灰度已完成且 passed=true |
| 监控未按客户过滤 | 确认 ① 已选中客户（namespace 传递正常） |

## 四、POC 操作速查

### 三种时间预算

<a id="poc-time-budget"></a>

| 级别 | 时间 | 步骤 |
|:---|:---|------|
| **轻量演示** | 4-6h | 加载模板 → 注入数据 → 跑通 3 个典型问题 → 客户确认 |
| **标准 POC** | 1-2d | 轻量 + 客户真实数据对接 + 初步效果评估 |
| **深度验证** | 3-5d | 标准 + 定制域 + 全流程优化 + ROI 评估 |

### POC 四阶段

| 阶段 | 做什么 | 耗时 |
|------|------|:---:|
| 准备 | 确认行业 → 加载模板 → 注入数据 | 30min |
| 注入 | 种子数据注入 + 验证成功 | 10min |
| 演示 | Chat 面板测试 2-3 个典型问题 | 30min |
| 汇报 | 展示 POC 结果 + 标出差距 + 提正式交付计划 | 15min |

## 五、反馈机制（AI 澄清引擎）

**浮动反馈按钮**位于工作台右下角。任意步骤中遇到问题，点击 → 描述 → 提交。

### AI 澄清流程

```
点击 [反馈] 按钮
    ↓
输入问题描述（如 "客户不太愿意配合"）
    ↓
AI 追问（根据当前步骤有不同追问方向）
    ↓
回答追问 → AI 继续澄清或结束
    ↓
AI 输出摘要 + 阻塞类型 + 根因 + 严重程度
    ↓
[提交澄清结果] → 存入 field_feedback/
```

### 各步骤 AI 追问重点

| 步骤 | AI 追问方向 | 示例追问 |
|:---|:---|:---|
| ① 业务认知 | 客户背景、组织关系、沟通盲区 | "跟你对接的人是啥角色？能拍板吗？" |
| ② 评估域 | 数据缺口位置、阻塞程度 | "这个域的通过率目前多少？缺哪种实体？" |
| ③ 问题重构 | 客户认可度、归因偏差 | "客户对你说的深层问题认同吗？" |
| ④ 验证价值 | POC 失败步骤、数据质量 | "POC 在哪一步挂的？模板加载还是回答？" |
| ⑤ 快速构建 | 打包失败点、环境差异 | "airgap 还是 online？日志报什么错？" |
| ⑥ 评测护栏 | 指标退化量、回滚判定 | "通过率从多少掉到多少？" |
| ⑦ 验收移交 | 签字卡点、阻塞根因 | "卡在谁那里？有替代方案还是纯粹不批？" |
| ⑧ 运营监控 | bug 分类、影响组件 | "是偶发还是持续？影响哪个组件？" |

### 跳过与提交

- 点击 **[跳过澄清，直接提交]** 可跳过 AI 追问
- **[提交澄清结果]**：反馈存入 `field_feedback/`，关联当前步骤和客户

## 六、工作流模式（多 Agent 协作）

标准交付流程可切换为 4 个专业 Agent 协作执行的 DAG。

### 四个 Agent

| Agent | 角色 | 类型 | 产出 |
|:---|:---|:---:|:---|
| **FDE业务分析师** (BA) | 收集客户信息 | 人工 | `customer_profile` |
| **FDE方案架构师** (SA) | 诊断 + 方案设计 | AI | `solution_design` |
| **FDE交付工程师** (DE) | 构建 + 部署 | AI | `deployment_package` |
| **FDE交付经理** (DM) | 验收 + 签字 | 人工 | `acceptance_report` |

### 启动方式

标题右侧下拉菜单 → 选择 "FDE 标准交付 v1" → 进度条自动切换为 4 步。

### 执行规则

- **人工步骤**（BA、DM）：FDE 手动完成，完成后标记该步骤
- **AI 辅助步骤**（SA、DE）：系统自动执行，FDE 审核结果
- **审批关卡**（BA、SA、DM）：关键产出需上级/客户确认后才能进入下一步
- **产出物传递**：每步完成后自动传递给下游

### 进度条颜色

| 颜色 | 含义 |
|:---|:---|
| 蓝色 | 当前步骤（第一个未完成的 Agent） |
| 绿色 ✓ | 已完成（output_artifact 已写入 pipeline_state） |
| 灰色 | 未开始（上游未完成） |

> 创建自定义工作流详见 [04 - 管理与扩展](./04-fde-admin.md#二创建-workflow)。

## 七、交付手册模板

交付完成时，系统自动生成标准交付手册。模板结构：

| 章节 | 内容 |
|------|------|
| 0. 行前检查 | 离线包、Agent/Skill/Workflow 可用性、样例数据、网络确认 |
| 1. POC 现场验证 | 1-2 天：环境部署 → 核心流程演示 → 客户数据对接 |
| 2. 正式部署 | 生产环境安装 → 配置迁移 → 性能调优 |
| 3. 培训交接 | 管理员培训（1h）+ 终端用户培训（1h） |
| 4. 售后支持 | 7 天关键期 + 30 天稳定期 + 巡检计划 |

### 行前检查清单

| 检查项 | 不通过时处理 |
|:---|:---|

| Workflow 节点拓扑完整 | 用 打开 /core/workflows（Workflow 管理页面）创建 |
| 样例数据已准备 | ④ → POC 工具箱 → 注入模拟数据 |

## 八、业务域数据建设（附录）

### 查看已有域

管理端 → 打开 /infra/ontology（本体模型） → 查看域卡片（实体数、通过率、Skill 绑定）

### 创建新域

1. 管理端 → 打开 /infra/ontology（本体模型） → **🤖 智能生成**
2. 输入域名 + 关键词描述（如 `lock-service` + "智能锁 安装工单 故障类型"）
3. AI 自动生成 YAML → **保存并注册**

### 注入种子数据

```bash
# 单个域
# 通过 ④ POC Tab → 快速数据注入操作
# 或通过 API 注入
curl -X POST "http://localhost:8003/api/platform/apps/fde/poc/inject" \
  -H "Content-Type: application/json" \
  -d '{"domain": "supply-chain"}'

# 所有域（通过多次 API 调用或 POC Tab 加载通用模板）
curl -X POST "http://localhost:8003/api/platform/apps/fde/poc/inject" \
  -H "Content-Type: application/json" \
  -d '{"profile": "poc-general"}'
```

### 域成熟度提升

| 当前状态 | 操作 |
|------|------|
| 无数据 | 注入种子 + 上传至少 3 份文档 |
| 通过率 <60% | 补充缺失实体类型 + 重新运行引擎 |
| 通过率 60-80% | 优化类定义 + 补充关系 |
| 通过率 >80% | 可交付 |

| 工具 | 位置 | 用途 | 何时用 |
