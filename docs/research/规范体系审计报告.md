# aiPlat 规范体系审计报告（规范是否正确、完整、够用）

> **审计对象**：aiPlat 文档系统中的规范体系——docs/standards（3 份）+ docs/policy + docs/compliance + docs/security + architecture/boundary_rules.yaml + 5 份 CLAUDE.md 的强制规则（核心 105 条 §5.x）+ arch_guard_rules.yaml（190 条）。
> **审计问题**：这些规范是否正确、完整？针对 aiPlat 系统是否够用？
> **审计方法**：全量定位 → 逐份阅读 → 规范 vs 代码事实对照 → 维度覆盖盘点 → 系统风险点盲区检测。
> **审计时点**：2026-08-15。

---

## 0. 总体判定（先给结论）

| 维度 | 判定 | 一句话 |
|---|---|---|
| **正确性** | ⚠️ 部分正确 | 规范内容本身合理（三 ID/鉴权/session 设计专业），但**全部 status: draft**（未定稿）；存在**规范要求 vs 代码实现矛盾**（如规范要求 mTLS，实际用 API key）；**规范未被完全执行**（24 项宪法违规对应规范条款） |
| **完整性** | ⚠️ 核心丰富、外围缺失 | aiPlat-core/CLAUDE.md **105 条规范**覆盖引擎/记忆/知识/Agent/Skill/工具等核心；但 standards/ 仅 3 份，**数据/DB、性能、命名、错误处理、前端、独立多租户规范缺失** |
| **够用性（针对 aiPlat）** | ⚠️ **不够** | 规范覆盖"内核/架构"充分，但**覆盖不了系统的实际风险**：①守卫 12 条 bug（规范无"规则自检"条款）；②能力登记双源漂移（规范无"单一真相源"条款）；③前端 326 文件无规范约束；④多租户/计费无专门规范 |
| **执行度** | ⚠️ 规范→规则→守卫链路存在但断裂 | 190 守卫规则覆盖部分规范（配置驱动/退化策略等），但 24 项宪法违规未被拦住（守卫误报掩盖） |

**一句话**：aiPlat 的规范**内核强**（105 条 engine 规范 + 190 守卫规则，是我见过的 agent 系统中最系统的），但**三个问题**：① 3 份 standards 规范全是 draft 且与实现有出入；② 覆盖偏"内核"缺"外围"（数据/前端/性能/错误处理/多租户无标准）；③ **规范→执行链路断裂**（规范写了，但守卫没拦住违规——24 项宪法违规就是证据）。

## 2. 正确性评估

### 2.1 ✅ 规范内容本身合理（抽样）

| 规范 | 内容质量 | 证据 |
|---|---|---|
| 三 ID 规范 | 分工清晰（request_id 幂等/run_id 生命周期/trace_id 观测）、幂等映射表设计、贯穿字段明确 | 规范正文 §1-3 |
| 鉴权规范 | JWT claims 最小集表、request_id 不进 JWT 的论证（"JWT 是可复用凭证"）、透传 header 规范 | 规范正文 §2-3 |
| session_id 规范 | "会话边界应绑定业务上下文容器而非用户"（防串话/越权）——**设计判断正确** | 规范正文 §1-2 |

### 2.2 ❌ 规范 vs 代码事实的矛盾

| # | 规范要求 | 代码实际 | 矛盾 |
|---|---|---|---|
| C1 | 鉴权规范："服务间鉴权优先 mTLS；若必须用 token 用 service JWT" | `authenticator.py:45` 实际用 **API key**（`apl_` 前缀 + sha256） | 规范（draft 理想）vs 实现（API key） |
| C2 | 三 ID 规范："request_id ≠ run_id（幂等分离）" | `job_scheduler.py:273` `request_id=run_id` | 实现将二者混用（潜在违规） |
| C3 | 三 ID 规范："request_dedup 幂等映射表" | 未发现 `request_dedup` 表实现 | 规范设计了，代码未实现 |

### 2.3 ❌ 规范未被完全执行（规范写了但违规存在）

| 规范条款 | 对应宪法违规 | 违规量 |
|---|---|---|
| core CLAUDE §5.7 单向依赖/门面 | harness→apps import | 53 处 |
| core CLAUDE §5.7 门面使用 | api→engine 直导 | 61 处 |
| 根 CLAUDE §8 内核无关 | kernel phase 字符串分支 | 3 处 |
| core CLAUDE §5.2 Schemas/提示词模板 | 模板占位符 `{}` 非 `{{var}}` | 1 处 |

**结论**：规范**写得对**（条款正确），但**执行断裂**——24 项宪法违规对应多条规范条款，守卫没拦住（12 条守卫 bug 误报掩盖 + 宪法测试未在 CI 生效）。

## 4. 够用性评估（针对 aiPlat 系统）

**规范"量"足够（300+ 条），但"对不上系统的实际风险"**：

| 系统实际风险（已知） | 有无规范覆盖 | 结论 |
|---|---|---|
| 守卫 12 条规则语法 bug（治理体系自身缺陷） | ❌ 无"规则自检/黄金样本"规范 | **盲区**——规范管系统，不管治理系统本身 |
| 能力登记双源漂移（registry 807 vs 文档 944） | ❌ 无"单一真相源/自动生成"规范 | **盲区**——规范要求登记但无校验规范 |
| 前端 326 文件无约束 | ❌ 无前端规范 | **盲区** |
| 24 项宪法违规（内核无关/职责归属被违反） | ✅ 有规范（§5.7/§8）但未执行 | **执行断裂** |
| 多租户/计费/配额 | ⚠️ 有零散提及无专门规范 | **半盲区** |
| 引擎层硬编码中文 prompt（历史） | ✅ 有（§5.29 内核无关）已修复 | 已覆盖 |

**核心判断**：aiPlat 的规范体系**"内核过度规范、外围规范缺失、自身无自检"**——对引擎/架构/安全规范得非常细（105 条），但对数据/前端/性能/错误处理/多租户几乎空白，且**没有规范约束治理体系自身**（规则没黄金样本测试 → 12 条 bug 无人发现）。

## 6. 结论

**aiPlat 的规范体系"内核很强、外围很弱、执行断裂"**：

- ✅ **内核规范是行业顶级**：105 条 engine 规范 + 190 守卫规则，覆盖架构/依赖/配置驱动/内核无关/记忆/知识/Agent/Skill/安全/模型——**"规范的量"绝对够**，甚至偏多
- ⚠️ **正确性有瑕疵**：3 份 standards 规范全是 draft（未定稿）、mTLS vs API key 矛盾、request_id=run_id 违规、request_dedup 未实现
- ❌ **完整性与够用性不足**：数据/DB、前端、性能、命名、错误处理、独立多租户**六大维度无规范**；更关键的是**没有约束治理体系自身的规范**（规则无黄金样本 → 12 条 bug 无人发现）
- ❌ **执行断裂**：规范写得对，但 24 项宪法违规证明**规范没被强制执行**（守卫误报掩盖 + 宪法测试未生效）

**一句话**：**针对 aiPlat 系统，规范"不够"——不是因为量少（300+ 条很多），而是因为①关键规范还是 draft、②覆盖偏内核缺外围、③没有治理"治理者"的规范、④执行链路断裂**。修复优先级：定稿 3 份 standards（P0）→ 规范自检黄金样本（P0）→ 单一真相源/前端/数据规范（P1）。

## 7. 审计方法局限

1. "规范 vs 代码矛盾"（C1-C3）基于 3 份 standards 逐条对照，未系统扫描全部 CLAUDE.md 条款 vs 代码
2. 维度盲区判定基于 standards/ 目录存在性 + CLAUDE 章节 grep，未逐一确认 CLAUDE.md 是否在某维度有隐藏条款
3. 105 条 core CLAUDE 规范未逐条验证执行状态（仅抽查 §5.7/§5.2/§8 对应宪法违规）
4. "300+ 条规范"为估算（含重复条款），实际独立规范数可能略低
