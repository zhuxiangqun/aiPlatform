## 4.5 结论与决策建议（直接回答三问）

### Q1 知识库管理方式正确/完备/需改善吗？

**架构正确**：多源摄取（wiki/KB/对话）+ 本体 ABox 构建 + CRAG 多级（本体图→FTS5→wiki→web）+ 三层租户隔离 + 质量监控——设计方向正确，工程化程度高。

**不完备（3 个实质缺口）**：
1. **"向量检索"是名义存在**：kb_embeddings 0 写入者；GraphRAG 的 _vector_search（retriever.py:263）docstring 称 vector store、实际调 wiki `search_pages`（伪向量）——**语义检索能力真实缺失**
2. **图存储两套**（kb_graph 死 + GraphIndex 活），本体事实拆分
3. **图增强静默死**（graph_enhance_query 绑定数 bug）+ 中文质量门失真

**需改善**：是——先修 P0（图增强 bug + 向量声明去留），再收敛图存储。

### Q2 向量数据库还需要吗？

**判断：当前不需要引入——现有 FTS5 + 本体图 + wiki 结构化查询已覆盖生产 RAG 主路径**（CRAG 第一级 GraphRAG 实体路由走 GraphIndex，实体命中后靠 wiki FTS 取块）。

**但语义检索是真实缺口**：FTS 无法处理同义改写/概念匹配/口语化 query（如"怎么改密码" vs 手册"账号密码重置流程"）。

**决策建议（v3 已执行）**：
| 场景 | 建议 | v3 状态 |
|---|---|---|
| 知识库以精确术语为主（设备/船舶/运维手册，query 术语化） | **不引入向量**，移除空壳声明 | 未走此路径（保留向量） |
| 用户 query 口语化/多样化（对话式知识问答） | **引入真语义检索** | ✅ **已执行（#53/#55）**：embedder 默认 semantic + `_vector_search` 真向量取块，GraphRAG 获得真向量层 |

**原则**：向量要么接线要么移除——当前"声明未接线"的空壳（kb_embeddings + 伪 _vector_search）最危险（让开发者误以为有语义检索）。

### Q3 本体模型建立方式正确吗？

**正确**：
- **TBox 配置驱动**：`~/.aiplat/ontologies/{domain_id}.yaml`（域专家 YAML 定义类/属性，无需写代码，ontology_loader.py:71）
- **ABox 双路径**：① 确定性构建（wiki frontmatter/KB 文档 → build_abox 三元组，knowledge_abox_builder.py:45）；② LLM 抽取（EntityExtractor）
- **T-Box 一致性校验**（validate_tbox：property domain/range 引用 class，knowledge_ontology.py:907）
- **实体消歧**（CrossDomainResolver 三级匹配）+ 消费活跃（GraphRAG/orchestrated_retrieval 3 生产调用者）

**需改善（3 点）**：
1. **ABox 类归属用通用类型**：page → `WikiPage/ConceptPage/TopicPage`（_build_wiki_triples:210-218），**未映射到域 TBox 的具体类**——实例与域本体类脱节，图查询难按域类过滤
2. **prop 未校验在 TBox**：_add_data 直接加 data property，未校验 prop 存在于域本体的 object/data property 定义
3. **类类型硬编码**：EntityExtractor 的 VALID_CLASS_TYPES（人物/组织/产品…）应读域本体 YAML 的类清单而非硬编码
