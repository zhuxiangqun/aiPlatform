# 代码 / 文档 / 代码图谱 / 能力图谱 四元同步体系元审计报告

> **审计对象**：aiPlat 的"代码 ↔ 文档 ↔ 代码图谱（CodeGraph）↔ 能力图谱（CapabilityGraph）"四元同步体系。
> **审计问题**：这个体系是否能够保证四者同步？覆盖哪些方向？自动还是人工？校验强度？已知断链在哪？
> **审计方法**：定位四实体 + 梳理全部同步/校验机制 + 实测双向漂移（代码符号 vs 文档 vs registry vs 图谱）。
> **审计时点**：2026-08-15。

---

## 0. 总体判定（先给结论）

| 维度 | 判定 | 一句话 |
|---|---|---|
| **四个实体是否都存在且真实** | ✅ 是 | 代码（源码）、文档（AIPLAT_CAPABILITIES.md 944 项）、CodeGraph（1657 节点）、CapabilityGraph（210 节点）全部存在 |
| **图谱与代码的同步** | ✅ **能保证**（自动化强） | CapabilityGraph 有 mtime 增量 + SQLite 持久化 + GraphSyncHandler 事件失效；CodeGraph 有缓存失效 + 持久化 |
| **代码→文档的同步** | ⚠️ 部分保证 | auto_sync_docs.sh 已接线（git hook），实测 harness 模块 0 gap；但 **registry→文档方向 56% 漂移** |
| **文档→registry 的同步** | ⚠️ **不能保证**（断链） | auto_register_capability.py / check_doc_sync.sh / generate_impact_matrix.py / check_code_doc_gap.py **4 个机制全部未接线** |
| **总体** | ⚠️ **部分保证** | **图谱侧同步强（全自动），文档侧同步弱（一半机制未接线 + 实测漂移）** |

**一句话**：aiPlat 的**图谱（CodeGraph/CapabilityGraph）与代码同步是自动且可靠的**；但**文档（CAPABILITIES/registry）与代码的同步体系不完整**——6 个同步机制只有 2 个接线，实测 registry 142 符号中 56% 不在文档（含 ModelManager 等核心符号），且两文件统计口径不一致（944 vs 807）。

## 2. 四元同步机制全貌（6 个机制 + 图谱侧 3 个）

### 2.1 图谱侧同步（CodeGraph + CapabilityGraph ↔ 代码）—— ✅ 自动且可靠

| 机制 | 方向 | 接线 | 实测 |
|---|---|---|---|
| **CapabilityGraph 增量重建** | 代码(AGENT.md/SKILL.md) → 图谱 | ✅ 内置（mtime 变化 ≤10 个文件 → 只重建变更目录） | 图谱 61 agent == 实际 4+57，83 skill == 53+30，**完全同步** |
| **CapabilityGraph SQLite 持久化** | 图谱 → 磁盘 | ✅ 内置（重启存活） | `_CAP_CACHE` + 持久化路径存在 |
| **GraphSyncHandler**（`graph_sync.py`） | 资源变更 → 图谱失效 | ✅ 接线（订阅 RESOURCE_MUTATED 事件，2s 防抖清缓存） | 消费者（overview/capability/diagnostics）自动重建 |
| **CodeGraph 缓存失效** | 代码变更 → 图索引失效 | ✅ 内置（mtime 检查 + 缓存 TTL） | 1657 节点缓存 valid |
| **CodeGraph SQLite 持久化** | 图索引 → 磁盘 | ✅ 内置（`code_graph_persist.py`） | `~/.code_graph.db` |

**图谱侧结论：自动、实时、可靠**——代码一改，图谱经事件/mtime 自动失效重建，无需人工。这是四元中**同步最健康的一环**。

### 2.2 文档侧同步（CAPABILITIES / registry ↔ 代码）—— ⚠️ 一半机制未接线

| 机制 | 方向 | 接线状态 | 性质 |
|---|---|---|---|
| **auto_sync_docs.sh** | 代码(新模块) → CAPABILITIES 自动补录 | ✅ **git hook:93**（仅 7 天 git log 的新模块） | 自动，但只补"新模块"级别 |
| **capability_guard.sh** | 代码 → CAPABILITIES 检查 | ✅ **git hook:35**（advisory，不阻断） | 只警告 |
| **auto_register_capability.py**（cap check） | 新公共符号 → capability_registry.yaml | ❌ **未接线**（仅独立命令 `cap check`，不进 git hook/CI） | 依赖人工跑 |
| **check_doc_sync.sh** | 代码 → 文档依赖检查 | ❌ **未接线**（且自身声明 "WARNING only, never blocks"） | 连上也不阻断 |
| **generate_impact_matrix.py** | registry → 影响矩阵 | ❌ 未接线 | 纯生成工具 |
| **check_code_doc_gap.py** | harness 模块 → CAPABILITIES | ❌ 未接线（--ci 仅警告，非阻断） | 实测 0 gap（当前无缺口，但机制未强制） |

**文档侧结论：机制存在但一半是摆设**——真正接线的只有 2 个（auto_sync_docs 自动补录 + capability_guard 警告），4 个校验/登记机制（cap check/check_doc_sync/generate_impact_matrix/check_code_doc_gap）全部未进强制链路，且 check_doc_sync 自身就声明不阻断。

## 3. 实测四元漂移（核心证据）

### 3.1 代码 → 文档方向：✅ 无 gap（harness 模块级）

```
python3 scripts/check_code_doc_gap.py → ✅ 所有 harness 模块已在 CAPABILITIES 中登记
```
- harness 模块级登记**完整**（auto_sync_docs 的 git hook 起了作用）

### 3.2 代码 → 能力图谱方向：✅ 完全同步

```
CapabilityGraph 210 节点: agent 4(engine)+57(workspace)=61 == 实际 4+57 ✅
                        skill 53(engine)+30(workspace)=83 == 实际 53+30 ✅
                        syscall 29 / tool 32 / mcp 4（与注册一致）
```
- **图谱侧零漂移**——增量同步机制真实有效

### 3.3 registry → 文档方向：❌ 56% 漂移（严重断链）

```
capability_registry.yaml 142 个 provides 符号中，80 个（56%）不在 AIPLAT_CAPABILITIES.md：
  ModelManager / PIIDetector(文档有3次命中? 需区分) / MCPRuntime / SkillRouter / IntentAnalyzer / MemoryEntry ...
```

**精确验证**：
- `ModelManager` 在文档 **0 次命中**（含中文"模型管理"也 0 次）→ **真实缺登记**（registry 有、文档无）
- `PIIDetector` 在文档 3 次命中 → 有登记（命名口径差异）
- **结论**：80/142 的"缺失"中，部分是命名口径（registry 符号名 vs 文档中文描述），但 **ModelManager 等核心符号是真实漂移**——文档 944 项声称全量，却缺 registry 已登记的核心能力

### 3.4 文档 vs registry 总量：❌ 不一致

```
AIPLAT_CAPABILITIES.md total_capabilities: 944
capability_registry.yaml total_capabilities: 807（各 domain caps_count 和 780，provides 实际 142）
```
- **三口径三数字**（944/807/780/142）——统计字段全部手工维护、无自动校验

## 4. 判定：该体系能否保证四元同步？

| 同步方向 | 能否保证 | 机制 | 缺口 |
|---|---|---|---|
| **代码 → 能力图谱** | ✅ **能**（全自动） | mtime 增量 + SQLite + 事件失效 | 无 |
| **代码 → 代码图谱** | ✅ **能**（全自动） | AST 构建 + 缓存失效 + SQLite | 无（未提交新文件不入索引，见元审计 §11） |
| **代码 → 文档（CAPABILITIES）** | ⚠️ **部分能** | auto_sync_docs（git hook）只补新模块 | check_code_doc_gap 未接线，符号级漂移不拦 |
| **代码 → registry** | ⚠️ **不能保证** | cap check 未接线 | 新符号不自动登记，靠人工跑 cap check |
| **registry → 文档** | ❌ **不能保证** | 无此方向机制 | **实测 56% 漂移**（ModelManager 等缺登记） |
| **文档 → registry** | ❌ **不能保证** | 无此方向机制 | 944 vs 807 三口径不一致 |

**核心结论**：
1. **图谱侧同步体系是健康的**（全自动、事件驱动、实测零漂移）——aiPlat 的"代码图谱/能力图谱"确实与代码保持同步
2. **文档侧同步体系有结构性缺口**——"能力登记"（registry）与"能力声明"（CAPABILITIES.md）之间**没有任何自动同步/校验机制**，导致 56% 漂移；6 个同步机制 4 个未接线
3. **同步是单向的**：代码→图谱 ✅、代码→文档 ⚠️；但**文档↔registry 双向都无保障**

---

## 5. 根因分析（为什么文档侧会断链）

1. **机制多但接线少**：6 个同步脚本只接 2 个（auto_sync_docs/capability_guard），且这 2 个都是"补录/警告"而非"校验阻断"
2. **cap check 是"人肉触发"**：auto_register_capability.py 作为独立命令存在，但未进 git hook/CI——开发者不主动跑就不登记
3. **双源设计缺陷**：CAPABILITIES.md（人类可读）+ registry.yaml（机器可读）**本应互为镜像，却无生成/校验关系**——两个"唯一真相源"谁都不唯一
4. **统计字段手工维护**：registry 的 total_capabilities/caps_count/total_domains 全是手填数字（807/780/32 与实际不符），无自动统计

## 6. 改进建议（按优先级）

| 优先级 | 项目 | 工作量 | 验收 |
|---|---|---|---|
| **P0** | 消除 registry→文档漂移：`auto_register_capability.py` 增加 `--sync-doc` 模式（把 registry 缺失符号写入 CAPABILITIES.md）或反向生成 | 1 天 | 80 个缺失符号补登，两文件口径统一 |
| **P0** | cap check 接入 git hook/CI（在 auto_sync_docs 后追加，新符号未登记即阻断） | 0.5 天 | 提交含新符号但未登记 → 被拒 |
| **P1** | registry 统计字段自动化：caps_count/total 由 provides 符号数 + 扫描自动生成（消除 944/807/780 三口径） | 1 天 | 三数字一致且随代码变化 |
| **P1** | check_doc_sync.sh 升级为阻断（当前 WARNING only）并接线 CI | 0.5 天 | 代码→文档断链阻断 |
| **P2** | 建立"单一真相源"：registry.yaml 为主，CAPABILITIES.md 由生成器产出（消除双源） | 2 天 | 只改 registry，文档自动更新 |
| **P2** | CodeGraph 纳入未提交新文件（`git ls-files --others`） | 0.5 天 | 新文件入索引 |

## 7. 结论

**aiPlat 的"代码/文档/代码图谱/能力图谱"四元同步体系是"一半健康、一半断链"**：

- ✅ **图谱侧（代码↔CodeGraph↔CapabilityGraph）同步可靠**：全自动（mtime 增量 + 事件失效 + SQLite 持久化），实测零漂移（61 agent == 实际、83 skill == 实际）
- ⚠️ **文档侧（代码↔CAPABILITIES↔registry）同步不可靠**：6 个机制 4 个未接线，registry→文档实测 56% 漂移（ModelManager 等核心符号缺登记），统计口径三数字不一致（944/807/780）
- **根源**：图谱侧是"事件驱动的自动同步"，文档侧是"人肉触发的半自动同步"——**自动化的部分可靠，依赖人的部分断链**

**一句话**：**这个体系能保证"图谱跟着代码走"，但不能保证"文档跟着代码走"**——能力图谱/代码图谱与代码的同步是 AI 时代的自动化范式（可靠），文档登记是传统的人肉流程（断裂）。修复方向是把文档侧也变成"生成器产出 + 校验阻断"（建议 P0/P1），与图谱侧对齐。

## 8. 审计方法局限（诚实标注）

1. registry→文档漂移（80/142）基于**符号名精确匹配**，未做中文描述模糊匹配——真实漂移数可能低于 80，但 **ModelManager 等已确认是真实缺登记**
2. CapabilityGraph 210 节点为当前快照，增量重建的"≤10 文件"阈值未做压力测试
3. CodeGraph 1657 节点覆盖全仓（含 platform/infra/app），但未逐一验证每个文件的图节点存在性
4. 同步机制的"接线状态"基于 git hook/CI/pre-commit 配置 grep，若存在其他触发路径（如 server 启动 hook）可能漏判
