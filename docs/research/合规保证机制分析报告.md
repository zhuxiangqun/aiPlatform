# aiPlat 合规保证机制分析报告（系统如何保证符合规范）

> **审计问题**：aiPlat 系统当前是如何保证"符合制定的规范"的？合规链路的每一层真实生效吗？
> **审计方法**：全量盘点合规检查工具 → 核实每层的调用位置（git hook/CI/pre-commit）→ 实测当前合规基线 → 判定每层"真实阻断/警告/断链"。
> **审计时点**：2026-08-15。基线：守卫 4 FAIL（§57/§73/§74/§17）+ 宪法 24 failed + cap check PASS。

---

## 0. 总体判定（先给结论）

**aiPlat 有一套"多层合规防御体系"，共 5 道防线（git hook → pre-commit 框架 → CI → 运行时守卫 → 文档验证），但当前状态是"**部分防线真实生效、部分断链**"：**

| 防线 | 真实生效？ | 现状 |
|---|---|---|
| **① git hook**（.git/hooks/pre-commit） | ✅ **生效**（10+ 步检查） | 编译/capability/boundary 同步/新 router/硬编码/auto_sync/接线/cap check/engine guard/architecture_guard |
| **② pre-commit 框架**（.pre-commit-config.yaml） | ❌ **未生效** | pre-commit 框架未安装，配置是摆设 |
| **③ CI workflow**（7 个） | ⚠️ **部分生效** | architecture-guard/contracts/genericity/pentest 存在，但 **constitution job 实际红（24 failed）**、caller_verify 跑废弃脚本 |
| **④ 运行时守卫**（architecture_guard.py） | ⚠️ **生效但有误报** | 12 条语法 bug 已修复（§73 误报消除），剩 4 FAIL（2 真 + 2 工具链） |
| **⑤ 文档/能力验证**（verify_evidence/cap/convergence） | ⚠️ **部分生效** | cap check PASS、convergence PASS、evidence 8 条 PASS；但 4 个机制未接线 |

**一句话**：合规保证**不是没有**（git hook 真实阻断 10+ 项），**但也不完整**——最关键的"宪法测试"防线在 CI 里是红的（24 项真实违规未被治理），且 pre-commit 框架整层未生效。**当前保证的是"增量合规"（新改动被拦），不是"存量合规"（已有违规未清）**。

## 2. 合规保证的"链路闭环"分析

### 2.1 当前实际闭环（增量合规 ✅）

```
开发者 commit
  → git hook（Step 1-8，真实阻断）
      ├─ 编译失败 → 拒
      ├─ 硬编码/接线/路由/cap/engine 违规 → 拒
      └─ architecture_guard --quick → 拒
  → CI（push/PR）
      ├─ ruff/mypy/pytest/coverage → 质量门
      ├─ contracts/genericity/pentest → 专项
      └─ constitution（红 ⚠️）
```

**结论：增量合规闭环真实存在**——新代码不合规（编译错/硬编码/未接线/未登记）会在 commit 时被 git hook 拦截。**这是"保证合规"的主要机制，且有效。**

### 2.2 断链处（存量合规 ❌）

| 断链 | 影响 |
|---|---|
| **宪法测试 24 failed 未治理** | 架构/内核/职责规范被违反的存量（harness→apps 53 处等）持续存在，CI 红灯长期未处理 |
| **守卫 4 FAIL 未清零** | §57 真违规 + §17 E2E 真失败未修 |
| **pre-commit 框架未装** | 第二层防线整层空转 |
| **4 个同步机制未接线** | 能力登记/文档同步的校验依赖人工 |
| **ratchet 泄压阀** | 已知债务可被写进 baseline 豁免（无 review 门禁） |

## 3. 合规保证的状态总结（诚实回答）

| 问题 | 答案 |
|---|---|
| **有没有合规保证机制？** | **有，而且是多层**（5 道防线，git hook 10+ 步检查） |
| **能保证新代码合规吗？** | **能**（git hook 真实阻断增量违规） |
| **能保证存量代码合规吗？** | **不能**（宪法 24 项违规 + 守卫 4 FAIL 存量未清） |
| **合规检查会阻断合并吗？** | ⚠️ 部分——git hook 阻断本地 commit；但 CI constitution 红灯未 gating（24 failed 仍可合入？需确认合并策略） |
| **合规是"自动闭环"吗？** | ⚠️ 半自动——自动检测 + 人工修复（违规发现后靠人改，无自动修复闭环） |

**最尖锐的问题**：宪法测试 24 failed 在 CI 中持续存在——**如果 CI 是合并门禁，这些违规应该早就被阻止了；如果 CI 不是门禁（只是信息性），那合规保证就缺了"强制执行"环节**。需确认 `.github` 的 PR 保护策略（branch protection 是否要求 CI 通过）。

## 5. 结论

**aiPlat 当前"如何保证合规"的答案：**

1. **主要靠 git hook（本地）+ CI（远端）两层真实检查**——git hook 10+ 步在 commit 时拦截增量违规（编译/硬编码/接线/路由/cap/engine），这是**真实生效的合规主防线**；
2. **cap check / capability_convergence / verify_evidence 真实运行**（PASS），保证新符号登记与声明可验证；
3. **但合规保证是"增量不完整"的**——宪法 24 项真实违规（存量）+ 守卫 4 FAIL 未清，CI constitution job 实际红；
4. **pre-commit 框架层未生效**（未安装），4 个同步机制未接线——合规体系有"空转层"和"未接线组件"。

**一句话**：**aiPlat 的合规保证是"强增量、弱存量、有断链"**——新代码被 git hook 严格拦（强增量），存量违规（24 项宪法 + 4 FAIL）未被治理（弱存量），pre-commit 框架和 4 个校验机制空转（有断链）。**要真正"保证合规"，需先把宪法 24 项清零 + 守卫 4 FAIL 清零 + 让 CI constitution gating，使存量与增量都合规。**

---

## 6. 审计方法局限

1. CI 是否真正 gating 合并（branch protection 配置）未核实——"24 failed 是否阻止合并"是推断（需查 GitHub 分支保护设置）
2. git hook 的"真实生效"基于文件存在 + 脚本逻辑，未实测提交触发（沙箱只读无法模拟 commit）
3. 各 workflow 的失败容忍度（allow-failure）未逐一核查——部分 CI job 可能标记为允许失败
4. 合规链路的"运行时状态"（server 启动时是否也跑守卫）未覆盖——本报告聚焦开发期合规
