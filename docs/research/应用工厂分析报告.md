# aiPlat 应用工厂（AI App Factory）分析报告（2026-08-22）

> **最后验证：2026-08-23**（L3 增量合并引擎实施后复核：merge_engine 已登记 capability_registry；代码证据见附录 A 及 `plan-app-factory-l3-incremental-engine.md`）

> 一句话：**应用工厂 = "AI 帮你做软件"的自动化产线**——你描述想要什么，它自动组一支"AI 团队"把东西做出来、测好、部署上线。像点菜：你说想吃啥，后厨（AI 团队）配菜、炒菜、试菜、上桌，你只管验收。

---

## 1. 它解决什么问题？

传统做软件：需求→设计→编码→测试→上线，要多个角色、数周时间。应用工厂把这条链**压缩成对话**：

| 传统方式 | 应用工厂 |
|---|---|
| 写需求文档 | 和 AI 对话，AI 自动整理成 PRD |
| 找开发/前端/测试 | AI 自动组队（按历史表现挑 Agent） |
| 写代码 | AI 生成（要么生成"Agent 配置"，要么生成真实代码） |
| 人工测试 | AI 跑测试并报告通过率 |
| 部署上线 | AI 部署到平台，你直接预览 |

**适用对象**：不懂代码的业务用户（一句话建应用）+ 懂技术的用户（精确控制生成过程）。

## 2. 入口与三种用法

入口在侧边栏 **"🤖 AI 应用工厂"**（唯一入口，旧的 /studio、/workbench 会自动跳过来）。进去后有三个 Tab，按你的熟悉程度选：

| 用法 | 适合谁 | 怎么用 |
|---|---|---|
| **快速开始** | 想直接上手的用户 | 选一个能力（如"数据录入""问答"）→ 填一句描述 → 一键开始，页面实时显示进度 |
| **对话式** | 需求还没想清楚 | 直接和 AI 聊天，它会追问澄清（"要几个人审批？""数据从哪来？"），聊完自动组队开工 |
| **高级配置** | 技术用户 | 能看到全部项目、手动调 Agent 组合/阶段/审批点，随时介入 |

## 3. 关键机制：AI 自己判断"该怎么做"（双模式）

这是应用工厂最聪明的地方——**AI 看了你的需求后，自动决定走哪条生产线**：

```
你的需求（如"做一个客服问答机器人"）
        ↓  AI 判断
   ┌────┴────┐
 对话型       计算型
（聊天/问答）  （查数据/算结果/表单）
   ↓           ↓
【Agent 模式】  【代码模式】
生成"AI 助手配置"  生成"真实程序代码"
（给平台配一个会   （像程序员写代码一样，
 对话的助手）      产出可运行的文件+测试）
```

- **Agent 模式**（默认，适合聊天机器人、问答助手这类）：产出的是"平台配置"——告诉平台"这里要一个会回答问题的助手"，由平台渲染成可交互页面。快，但不产生独立代码。
- **代码模式**（适合数据处理、CRUD、上传转码这类）：产出的是**真正的源代码文件**，会落盘保存，并**真的跑测试**（pytest）验证。

判断标准一句话：**"这东西的核心是'和人聊天'还是'算东西/存数据'？"**——前者走 Agent，后者走代码。

## 4. 从需求到上线：你看到的全过程

```
第1步 对话澄清   你和 AI 聊需求（它会参考公司知识库，更懂你）
第2步 确认 PRD   AI 把聊天的结果整理成《需求说明书》，你确认
第3步 自动组队   AI 按需求类型 + 各 Agent 的历史表现，组一支团队
第4步 团队干活   PM→架构师→开发→前端→测试 依次执行（关键节点暂停等你审批）
第5步 你审批     架构方案、测试用例等关键环节：通过/打回重做
第6步 自动修复   测试失败 → AI 自动找问题、改、重测
第7步 部署上线   通过后部署，给你一个链接直接打开看效果
第8步 随时改     「重新编辑需求」或回滚到任意阶段，重来
—— 改造老项目时（L2-L5 演进链路，见 §9）——
第9步 导入既有代码  上传 zip/路径 → 文件清单 + 修改意图
第10步 增量合并审批  选择"重写"或"增量合并"→ 逐文件 diff 审批（原子化）
第11步 数据库迁移    模型变更 → up/down DDL 预览 → 破坏性确认 → 应用
第12步 受控发布      版本化产物 → 金丝雀（权重）→ 全量/回滚
```

> **审批点设计**：不是全自动黑箱——架构、测试用例这些"关键决策"会停下来等你点头（HITL 机制）。你可以完全放手，也可以全程盯。

## 5. 和公司其他能力怎么配合

- **知识库**：AI 和你对话时，会检索公司已有资料当参考（不是凭空猜）
- **Agent 体系**：组队时参考每个 Agent 过去"一次通过率、被打回率"，挑靠谱的
- **数字人"小朱"**：在应用工厂页面，可以直接问小朱"有几个项目在跑？平均通过率多少？"
- **部署平台**：成品部署到统一的应用区（端口 8004），和平台其他应用一起管理

## 6. 权限：谁能用

| 操作 | 权限 |
|---|---|
| 创建项目/团队 | **管理员**（admin） |
| 对话/审批/查看/部署 | **Builder 角色**（普通参与即可） |

## 7. 诚实地说：5 个要知道的边界

1. **"通过率"有两种来源**——真跑过测试的（可信）和 AI 估算的（仅参考）。现在的版本会明确标注：`real_pytest`（真测试）或 `estimated`（估算）。看到 100% 先看是不是估算的。
2. **前端页面是"搭积木"**——无论哪种模式，页面都是平台预置的 5 种组件（表格/表单/上传/看板/聊天）拼出来的。**复杂、高度定制的界面做不了**，那是前端开发的活。
3. **测试好坏看 AI 生成的用例**——代码模式真跑 pytest，但测试用例本身是 AI 写的，AI 用例写得松，全绿也不代表真的没问题。
4. **两个入口有点重**——`/app/factory` 是完整入口，但 `/app/builder/projects`（纯列表）也能直达，可能让人疑惑。
5. **已部署应用的可见性**——任何 Builder 角色都能看到全部已部署应用，没有按项目的细粒度隔离。
6. **改既有代码是"重写"或"增量合并"二选一（L2/L3 语义）**——导入后可选"整文件重写（L2）"或"增量合并（L3，推荐）"：L3 只重生成受影响文件、diff 逐文件审批（原子化，全过才应用）、格式噪音自动折叠。金丝雀发布前仍建议跑真实测试（estimated 有提示）。

## 9. 演进链路：从"改单个文件"到"受控发布"（L2→L5，2026-08-22~23 全落地）

应用工厂从"从 0 到 1 生成器"演进为"从 1 到 100 演进器"的完整链路（设计文档：`plan-app-factory-l2-import-repo.md` → `l3-incremental-engine.md` → `l4-multi-module.md` → `l45-db-migration.md` → `l5-cicd.md`）：

| 层 | 能力 | 关键机制 |
|---|---|---|
| **L2 导入既有代码** | zip/路径 → imported/（隔离）→ manifest | zip-slip/密钥过滤/限额 + 意图锚点 {path, intent} + 重写行为契约 + skip_pytest_gate 逃生 |
| **L3 增量合并** | 逐文件 diff 审批（原子化） | 全文件输出 + 系统 difflib 计算；语法 py_compile + 接口 AST 门禁；哈希锁防并发覆盖；格式噪音折叠 |
| **L4 多模块编排** | 模块化系统演进 | modules.json + 跨模块影响（API/entity/事件契约 → 依赖图）+ 拓扑顺序编排 + 跨模块 merge 契约门禁（v1.5） |
| **L4.5 数据库迁移** | 模型变更 → up/down DDL | AST 提取 SQLAlchemy/Pydantic；破坏性（删列/类型变更）需显式确认；迁移历史 append-only + 回滚 |
| **L5 受控发布** | 版本化 + 金丝雀灰度 | releases/v{ts} + 发布状态机（ready→canary→full→rolled_back）+ canary_weight 权重路由（v2）+ infra 注册（CoreFacade 桥接）+ 迁移先行门禁 |

**演进闭环**：AI 改模型 → 增量合并审批（L3）→ 数据库迁移（L4.5）→ 版本化发布（L5）→ 金丝雀验证 → 全量/回滚——代码、schema、发布三者同步受控演进。

**代码证据**：`builder_project_service.py`（import_repo/merge_preview/merge_apply/migration_preview/create_release）、`builder/merge_engine.py`（ImpactAnalyzer/DiffMerger）、`builder/cross_module.py`（CrossModuleAnalyzer）、`builder/schema_migration.py`（SchemaExtractor/MigrationGenerator）、`builder/release_engine.py`（发布状态机）、`core/harness/infrastructure/infra_bridge.py`（deploy_app_service 桥接）、`core/harness/execution/pipeline_engine.py`（inject_imported_context/skip_pytest_gate/UNCHANGED 剔除）、前端 `Factory/index.tsx`（导入面板/合并审批/模块面板/迁移面板/发布区）。

**验证**：L2 34 + L3 25 + L4 21 + L4.5 18 + L5 23 = **121 例测试**全部通过（2026-08-23 复核）。

## 8. 总体评价

| 维度 | 星级 | 一句话 |
|---|---|---|
| 设计思路 | ⭐⭐⭐⭐⭐ | AI 判断需求类型自动选生产线，很聪明 |
| 能力真实度 | ⭐⭐⭐⭐ | 代码模式真生成文件、真跑测试，不是演示 |
| 工程完整度 | ⭐⭐⭐⭐⭐ | 从对话到部署全链路都有，还有审批/回滚/修复 |
| 透明度 | ⭐⭐⭐⭐ | 通过率已标来源，但估算精度仍有限 |
| 扩展性 | ⭐⭐⭐⭐ | 加新团队=加一个配置模板，不用改引擎 |

**总体判断**：应用工厂是 aiPlat 最接近"AI 代替人做软件"的能力——**真实可用、链路完整**。它的定位是"**快速搭轻应用**"（数据录入/查询/看板/问答），不是"替代专业开发做复杂系统"。对业务用户是极大提效，对技术用户是可配置的自动化产线。知道边界、按需使用，就是它的正确打开方式。
