## 2. 已确定的产品决策

### 2.1 P0 交付七张对象现状卡

对象：Agent、Skill、Prompt、KB/RAG、Arena、Code Review、Session。

每张卡只盘点当前实现，不要求完成新指标设计、算法校准或代码实现。每张卡一页，包含以下九项，并在页首记录 owner、日期、runner/judge 版本：

1. 对象/场景：评什么；
2. 当前 runner/judge；
3. 任务集和现有样本量；
4. 当前实际测量的维度；
5. 判定方式：exact/rule/gold/human/LLM judge；
6. 是否进入 composite：是/否/部分；
7. 空回复、超时、缺 gold 等失败处理；
8. 证据等级：smoke/fixture/gold/human；
9. 不能推出什么，以及是否允许进入发布 gate。

P0 卡片是现状盘点，不能用计划中的目标指标冒充现有能力。Arena/Session 等可以明确注明 `heuristic` 或 `fixture`，并写明不单独作为发布质量 gate。每卡估算约 0.5 人日，七卡合计约 3.5 人日；卡片 owner 对内容负责，Evaluation owner 汇总。

七张卡统一使用本计划附录 A 的字段模板，集中存放并使用相同命名规则；不得由各对象 owner 自行删改必填字段。模板本身只规定记录格式，不代表新的评分设计。

### 2.3 G2b-100 预注册和三方签认

在新增标注开始前完成 `G2B_100_PROTOCOL.md`，由以下三方签认：

| 角色 | 责任 |
|---|---|
| Evaluation 产品负责人 | 任务范围、风险接受、最终结论/claim 文案 |
| 评测方法负责人 | 分层、抽样、rubric、统计方法和门槛 |
| 独立 QA/标注协调人 | 双人独立、盲标、仲裁和数据完整性审计 |

预注册建议的任务边际配额：

| 分层 | 数量 | 任务范围示例 |
|---|---:|---|
| Prompt | 15 | 指令遵循、格式、拒答 |
| KB/RAG | 20 | 检索、来源支持、引用 |
| Code Review | 15 | finding 匹配、P0 覆盖 |
| Agent/Skill | 15 | 任务完成、工具/触发行为 |
| Session | 15 | 2–8 轮、目标保持 |
| Safety/Refusal | 20 | 注入、越权、拒答 |
| **合计** | **100** | |

另记录难度 easy/medium/hard = 30/50/20、来源至少 50 条真实任务/30 条 curated regression/不超过 20 条 adversarial-edge、语言比例建议中文 70%/英文 30%。这些是**边际配额**，允许交叉分层；真实来源、对象类型、难度与语言之间的交叉表也要保存，避免某一类指标完全由单一来源/语言驱动。实际配额须经三方在标注前确认。

建议预注册候选门槛：

| 条件 | 候选门槛 |
|---|---|
| 样本/标注 | n=100；两名不同标注者独立盲标；分歧按预定 rubric 仲裁 |
| 总体 benchmark pass rate | ≥80% |
| Wilson 95% CI 下界 | ≥70% |
| 工程/数据质量门的 inter-annotator κ | ≥0.60，并报告原始 agreement、标签分布及仲裁率 |
| scoped benchmark 表现报告的标注可靠性门 | κ ≥0.70；或 κ ≥0.65 且同时满足 protocol 预注册的争议/仲裁上限、盲标和抽查条件。此门只衡量标注可靠性，不证明模型准确 |
| Safety / Code Review P0 切片 | 报告样本量和精确区间；只有达到 protocol 预注册的最低样本数时才允许作切片门槛判断。Safety n<20 时默认 report-only |
| 数据完整性 | 无缺项；无同人双填；无 gold 泄漏；model/prompt freeze 和数据来源可追溯 |

未同时满足时，可发布 scoped observed pass rate 和 CI，但不得提升为准确率 claim。即使满足，也只能报告限定 benchmark、模型版本和任务范围的 pass rate，不得称为通用准确率或认证。κ 是标注一致性，不是准确率；κ 门槛不能单独开放任何模型准确率 claim。总体 pass-rate 门槛也须保持为预注册的候选值，三方先检查任务权重、CI 下界规则和用途风险，再签署最终 protocol。由于 n=100 包含不同对象的分层任务，整体结果应称为按预注册配额加权的 benchmark pass rate，并同时报告各对象切片；不得将其外推为真实用户任务总体准确率。

Safety/Refusal 目标设为 20 条；若经方法负责人评估无法满足，则保留 n=10 并将该切片明确设为 report-only，不得据此宣称 Safety 切片通过。Code Review P0 切片同样需设最小样本量，低于最低量时只报告结果和区间。

#### G2b 相关样本、加权与切片解释

- 总体 pass rate 按 protocol 冻结的对象边际配额加权；必须同时披露各对象原始 n、通过数和未加权结果。它描述的是该 benchmark 配额下的结果，不是线上任务分布估计。
- Wilson 95% 区间作为常规二项描述区间报告，并明确其独立样本假设可能不适用于同一对象/任务族内相关的样本；不得将其单独描述为严格的总体推断区间。
- 若要作 scoped claim，方法负责人须在签署 protocol 前定义任务族/cluster 单位、重抽样方案和区间算法。确认性区间优先采用按任务族聚类的 bootstrap（或预注册且论证充分的 cluster-robust 方法）；cluster 数量不足以支持稳定估计时，只报告描述性结果，不作确认性 claim。
- Safety n=20 可报告该 benchmark 中的切片结果与区间，但不自动构成“安全通过”。Code Review P0 低于预注册最低 n 时只作 report-only。多切片比较默认不作显著性宣称；如需检验，须预注册多重比较控制方法。
- 任一切片不得借用总体 CI 或总体通过门槛宣称该切片通过；报告须列出切片 n、通过数、区间方法及限制。

Protocol 还须指定 **model/prompt freeze owner** 和明确的 freeze 时间戳。该 owner 在确认性运行前记录模型标识/版本、prompt 与配置版本或 hash、运行参数，并确认确认性数据未用于调参；模型或 prompt 在运行后发生变化即视为新 benchmark 版本或开发运行，不得沿用原确认性结论。

预先写入报告的 claim 模板：

> 在 **[benchmark 名称/版本]**、**[模型及版本/标识]**、**[prompt/config 版本]** 和 **[任务范围]** 上，n=[ ]，按预注册配额加权 pass rate 为 [ ]；[区间类型/方法] 95% CI 为 [ ]；双标一致性 κ=[ ]，仲裁率=[ ]。该结果仅描述此 benchmark 与配置，不能推出通用准确率、其他任务分布表现或安全认证。

#### G2b holdout 统计设计约束

“100 条中留 20 条 holdout”与“在 100 条上做最终门槛判断”只有在防止调参泄漏时才一致。预注册必须二选一并写清：

**推荐方案 A（n=100 作为确认性 benchmark）：** 100 条全部在模型/prompt 冻结后运行，标注和结果不反馈给优化环节；可将其中 20 条设为额外封存的泄漏哨兵，但只要团队可接触其结果，就不得再以该版本宣称未见测试。总体门槛按 100 条计算。

**备选方案 B（80 条开发集 + 20 条 holdout）：** 80 条可用于调试/校准，只有 20 条是确认性 holdout。此时门槛和 CI 必须按 n=20 预注册；不能把 80 条开发数据与 20 条 holdout 合并后称为未见测试。若需 n=100 的确认性精度，则另需 100 条封存评测集。

方法负责人应在 protocol 签署前选择方案。任何模型、prompt 或阈值调整若使用了确认性数据，须标记该 benchmark 已用于开发，并创建新版本/新确认集。

#### G2b 工时估算

当前 n=30 到目标 n=100，剩余 70 条。若每位标注者每条约 5 分钟，双标纯标注约 `70 × 2 × 5 = 700` 分钟，即 **11.7 人时**；另需培训、协调、仲裁、抽查和统计时间。若 100 条从零开始双标，则纯标注约 **16.7 人时**。完整预算按 **25–30 人时**预留，标注前以小批试标校准耗时。仲裁工时不能从 κ 直接推算：κ 受边际标签分布影响，不等于原始一致率；应根据 pilot 的实际分歧数和仲裁耗时更新估算。

### P1 版本迁移原则

所有会改变历史分值含义的修改都采用新 schema/judge version：

- 新旧结果并存，明确 `eval.score.v1`/`eval.score.v2` 或最终批准的命名；
- 历史报告不静默重算；
- 趋势图默认只比较相同评分版本；跨版本显示“不可直接比较”；
- 在新版本完成影子运行和差异分析前，不替换旧门禁口径；
- runner、rubric、模型、数据集任一变化均记录版本和运行参数。

### P1 门 B 验收

- 七张卡升级为可复现判分卡，评分条件和判定失败均可解释；
- 弱代理不再被展示为正式质量指标或独立门禁依据；
- 新旧 scoring version 分开存储和展示；
- Prompt/KB 路径清晰标示；
- G2b 有双标、仲裁、分层和统计证据；
- 结果只作 benchmark 范围内声明，不自动打开通用 accuracy claim。

## 5. P2：3–6 个月或独立立项

P2 不纳入本次 P0/P1 完成定义，不阻塞两者：

1. 上下文管理：长上下文召回、摘要保真、冲突处理、截断降级。
2. 持久记忆：写入、Recall@k、更新/过期、删除、租户隔离、污染抵抗。
3. 自学习：更新前后、迁移、遗忘、错误反馈抗性、追溯与回滚。
4. Evaluator calibration：人工抽样复核评估器误报/漏报/漂移；该机制是自学习可信度的前置条件。
5. 生产治理：动态 tenant、retention/删除策略、cohost SLO/灾备和 staging/B4-S/B5/B6。

每项先立明确 owner、风险评估、数据要求和预算，再排期；不能以“补几个 fixture”估算研究型能力。**P2 不得因临时需求插入 P0/P1 当前迭代；若确需插入，必须由产品负责人批准并从 P1 替换等量工作，不得无净增量扩张本期承诺。**

## 6. 证据等级与 E0–E5

不另建一套与项目 E0–E5 并行的正式成熟度等级。**评测方法负责人须在 P1 第 2 周前**盘点 E0–E5 的现行定义并提交 EET-1..4 映射表；由项目治理 owner 批准。若映射无法形成，保留 smoke/fixture/gold/human 作为证据类型标签，不发布第二套正式 gate 等级。

## 9. 变更控制

- **Protocol 冻结：** G2B-100 protocol 经产品、方法和独立 QA 三方签署后，任务配额、抽样/加权、门槛、区间方法、切片最低样本量和 claim 范围不得根据观察到的结果追溯修改。确需变化时创建新 benchmark/protocol 版本，并重新标明哪些数据用于开发、哪些仍为确认性数据。
- **评分口径版本：** runner、rubric、judge、模型/prompt、score schema 或数据集的变化，只能通过新版本记录；不得静默覆盖旧结果或回写历史报告。历史结果不自动重算，跨版本比较须标为不可直接比较，遵循本计划第 4 节迁移原则。
- **旧入口策略：** 当前执行基线为 #592 硬切，旧 URL 预期 404，不设 redirect 兼容期。若要恢复兼容，必须先经产品负责人批准变更，说明外部引用证据、目标期限和移除日期，并更新本计划及验收标准。
- **范围与容量：** P0/P1 新增工作须由产品负责人批准，写明负责人、估时、依赖，并从当前阶段替换等量工作/容量；不得净增本期承诺。P2 插入同样遵守等量替换。若涉及门槛、数据或发布验收标准的实质改变，必须形成新版本并重新审批，不得事后降低标准以追认通过。
